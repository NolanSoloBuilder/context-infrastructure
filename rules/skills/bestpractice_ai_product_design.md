## 线性聊天 vs 非线性知识工作的根本矛盾

### 问题本质

AI 产品的主流形态是"线性聊天入口"（ChatGPT、Claude Chat），但知识工作的本质是非线性的：
- 思考跳跃、分支、回溯
- 需要多文档并行参照
- 需要可视化结构（脑图、大纲）

### 矛盾表现

- 用户被迫在单一线程中处理复杂问题
- 上下文线性堆积，难以定位关键信息
- 无法并行探索多个思路

### 设计启示

- 线性聊天适合简单问答，不适合深度知识工作
- 知识工具需要支持非线性结构（分支、链接、可视化）
- 考虑"对话+文档"混合形态

## 感知与规则解耦原则

### 架构决策

将"感知层"（Perception）与"规则层"（Rules）严格分离。

### 感知层职责

输出原始感知信号：
- 车道位置、线型
- 车辆朝向角
- 道路上下文

### 规则层职责

基于感知信号进行业务判断：
- 什么是"偏离"
- 何时告警
- 告警级别

### 解耦收益

1. **快速迭代**：产品规则可独立修改，无需重新训练模型
2. **个性化**：不同客户/地区可有不同规则
3. **可审计**：规则变更可追溯，模型输出稳定
4. **LLM 集成**：未来可用 LLM 灵活组合信号

### 适用场景

- 安全关键系统（需要确定性规则）
- 多市场/多客户产品（需要个性化）
- 需要快速迭代的业务逻辑

## 一刀切产品定义的陷阱

### 问题

"一个产品满足所有客户"在多样化需求面前必然失败。

### 根因

- 不同客户的使用场景差异巨大
- 风险承受度不同
- 业务流程不同

### 解决方案

- 提供可配置的参数和规则
- 让 PM 或未来 LLM 灵活组合信号
- 将"什么是好"的定义权交给用户

### 案例启示

LDW 车道偏离预警：不同客户对"偏离"的定义、告警时机、容忍度完全不同。

## Guideline 过载问题

### 现象

10 页 Guideline 直接作为 Prompt 会 Confuse LLM，无法进行精细的 Trade-off 处理。

### 这是通用大模型的硬伤

- LLM 不擅长同时处理大量约束
- 约束之间可能存在隐含冲突
- 缺乏业务上下文理解

### 解决方案

1. **结构化约束**：将 Guideline 拆分为独立规则，逐步应用
2. **Few-shot 示例**：用案例替代长文档
3. **混合架构**：LLM 处理感知，确定性程序处理规则

## 设计能力进入 Agent 系统：声明、契约、证据、门禁

### 核心判断

AI 生成 UI 的质量瓶颈通常不在模型是否见过足够多的页面，而在团队的设计判断有没有被写成可读取、可调度、可验证、可回流的系统合同。

设计能力进入系统时，至少要覆盖四层：

1. **声明**：任务成立条件、业务语义、视觉事实、组件语义、页面骨架和工艺标准。
2. **契约**：skill 决定何时加载哪些声明、按什么顺序执行；evaluator 决定怎样检查和回流。
3. **证据**：DOM / CSS QA、页面画像、关键交互、截图和真实运行状态共同说明产物实际呈现了什么。
4. **门禁**：模型解释证据，确定性运行时重算分数、处理阻断问题并决定放行。

### 单一事实源优先

`spec.md`、`domain.md`、`craft.md`、`design.md`、`components`、`template` 表达的是六类责任，不要求机械创建六份文件。项目已有 `Profile`、PRD、schema、design tokens、组件文档或模板目录时，优先映射和增强现有资产。

一个判断只能有一个正式真源。skill 负责调度，不重新定义任务；evaluator 负责验证，不替生成器补交付；组件目录负责语义边界，不接管业务状态定义。

### GenUI 与 A2UI 边界

稳定页面、固定设置、长期信息架构和重复审批流继续使用预先设计的 UI。只有任务路径、判断依据或用户决策点会随上下文变化时，才引入 GenUI。

Agent 输出结构化界面意图、状态、内容、动作和阻塞条件；客户端保留组件选择、视觉 token、本地化、权限、校验、无障碍、降级和审计控制权。生产合同还必须覆盖版本、schema、幂等、超时、取消、重试、流式更新和 provenance。

### 评估职责分离

- 浏览器与运行时负责事实：页面真实打开、截图、DOM、关键点击、错误和数据链路。
- 模型负责解释：事实影响了哪个质量维度，为什么需要扣分或修改。
- 确定性程序负责裁决：按检查项和权重算分，应用阻断规则，输出放行结论。

平均分不能抵消主任务不清、领域逻辑错误、关键路径断裂、AI 回答无证据、权限失控或缺少真实验收证据。未通过时，回流任务必须包含问题、证据位置、责任真源和下一轮修改方向。

### 标准维护

所谓自我进化，本质是 evaluator 引导的生成循环与人维护的离线标准。权重、阈值和阻断项要用好案例、坏案例、混合案例、边界案例和品类案例校准，并持续检查误放行与误退回。

## Multi-Agent 设计原则

### 核心洞察

LLM 存在固有的"个性"（Personality）：
- O3：擅长搜索、探索，但分析较浅
- Gemini：搜索弱，但分析深入、综合能力强

这种个性难以通过 Prompt 改变。

### 设计启示

1. **利用互补优势**：让不同模型做自己擅长的事
2. **不要模仿人类角色划分**：PM/QA/Dev 是人类组织模式，不适用于 Agent
3. **上下文窗口分离**：不同 Agent 负责不同上下文子集
4. **必要时强制交接**：当模型抗拒指令时，通过代码强制切换

### 当前阶段建议

结合硬性规则和 AI 能力的混合系统，比纯粹的 Agentic 系统更可靠。

## 产品定义先于工程实现

### 核心瓶颈

闯红灯检测等项目的核心瓶颈是缺乏 PRD，而非技术能力。

### 策略

- 将 RFC 会议转为 PRD 讨论
- 先明确产品需求，再讨论工程细节
- "什么是我们想要的"比"怎么实现"更重要

### 因果链

产品形式 → 评估方式 → 模型开发策略

起点是清晰的产品定义。

---

## 注意事项

- 考虑多市场/多地区的法规差异
- 安全关键系统需要确定性兜底
- 用户信任建立难、破坏易
