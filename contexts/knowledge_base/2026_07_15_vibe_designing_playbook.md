# Vibe Designing Playbook：把设计判断变成 Agent 可执行的系统能力

## 来源与核对范围

- 官网：[Vibe Designing Playbook](https://alibaba-cloud-design.github.io/vibe-designing-playbook/)
- 公开仓库：[Alibaba-Cloud-Design/vibe-designing-playbook](https://github.com/Alibaba-Cloud-Design/vibe-designing-playbook)
- 核对日期：2026-07-15
- 核对材料：官网完整正文、仓库 README、12 份公开附件、188 条设计词典源码、公开仓库目录。

公开仓库能核对 Playbook 正文、简化版声明/契约示例和词典。第三章提到的完整 `Evaluator/` 运行时、schema、prompt、校准样本和 CLI 没有包含在当前公开仓库中，因此本文把它们视为作者公开描述的内部实践，不能当作已经从代码层复验的开源能力。

## 一句话判断

这份 Playbook 讨论的并非怎样让 AI 画出更漂亮的页面。它试图建立一套设计能力的编译链：设计师先把隐性的判断写成声明，再用 skill 和 evaluator 把声明接入生成流程；运行时只让 Agent 声明意图，由客户端控制渲染；生成后用浏览器证据、模型判断和确定性门禁决定放行或回流。

它最有价值的主张是：模型生成质量受限于系统里有没有明确的判断接口，而不只受限于模型能力或 Prompt 技巧。

## 它在讲什么

全书分成三段，但三段属于一条连续链路。

### 1. 设计工程：生成前把判断写进系统

作者把一次页面生成分成理解规划、搭骨架、填充、细化、评估五个环节。颜色、间距、字号等 token 从骨架阶段开始持续约束全链路；评估失败后，问题应回到负责它的上游材料，而不是在最终页面上反复追加局部 Prompt。

这套输入被分为六份设计声明和两份执行契约。

| 资产 | 回答的问题 | 典型缺口 |
| --- | --- | --- |
| `spec.md` | 功能怎样才算成立 | 主流程存在，但空态、错误态、权限态、恢复路径和验收标准缺失 |
| `domain.md` | 业务对象、状态、风险与权限意味着什么 | 页面可用，却不像真实业务，甚至表达了错误业务语义 |
| `craft.md` | 排版、层级、材质、动效怎样使用才克制 | 蓝紫渐变、等大白卡、玻璃态和无意义动效成为默认答案 |
| `design.md` | 视觉意图、角色、token、派生和缺口怎样管理 | 裸写色值、尺寸与时长，状态变体临时新造 |
| `components` | 哪些组件可以用，各自承担什么语义 | Badge / Tag、Dialog / Drawer 等外观接近的组件被混用 |
| `template` | 某类任务应该从什么页面骨架开始 | 控制台被做成营销页，看板退化成卡片墙 |
| `skill` | 何时读取哪些声明，按什么顺序执行 | 规则存在于文档里，却没有进入 Agent 的调用路径 |
| `evaluator` | 怎样检查产物、定位责任并触发回流 | 评审只剩下“再优化一下”这类无法执行的意见 |

这里真正有用的是责任边界。`domain.md` 决定失败、高危、未知等状态的业务含义；`design.md` 提供可用的视觉角色和 token；`craft.md` 判断这些视觉能力是否使用得当。三个文件都可能涉及颜色，但负责的是三种不同判断。

作者对 `design.md` 的定义也超出了 token 表。它从视觉意图、视觉角色、值系统、派生机制、组件状态与响应式、图形与典型表面，一直覆盖到执行约束和缺口记录。找不到 token 时，Agent 应采用有记录的 fallback，或拒绝生成相关部分，并写入 `gaps.log`。设计系统缺口因此成为可见输入，而不是被一个临时字面量藏进代码。

### 2. 动态交互：运行时围绕意图组织界面

第二章从 UX 转向 AX（Agent Experience）。传统 UX 帮用户把目标翻译成操作；Agent 压缩了这段执行距离，随后放大了评估难题：用户没有亲手完成每一步，更需要知道 Agent 做了什么、依据是什么、哪里不确定，以及怎样撤销、纠正或恢复。

作者把 GenUI 定义为运行时的界面组织方式，而不是让模型自由生成 HTML。只有任务路径、判断依据或用户决策点会随上下文变化时，才适合动态生成；仪表盘、设置页、固定审批流和长期信息架构仍应保持稳定。

A2UI 是 GenUI 的一种受控实现：

```text
Agent：声明 intent、status、context、content、actions、behavior
Client：选择受控组件，应用 token、无障碍、校验、权限和降级规则
User action：以结构化事件写回 Agent 上下文，任务继续推进
```

Agent 决定“此刻需要表达什么、需要用户做什么判断、是否阻塞后续执行”，客户端决定“按钮、卡片、状态和布局怎样呈现”。这条边界让动态性和产品控制权同时成立。

书中用三种界面承接一条任务链：OmniBox 收集目标、对象、时间、数据范围和历史上下文；FlexCard 承接澄清、授权、风险确认等中间判断；GenReport 把复杂结果变成可保存、分享、追踪和继续操作的 Artifact。

### 3. 自我进化：生成后用证据和门禁迭代

这里的自我进化并非模型自行学习。准确说，它是 evaluator 引导的生成循环，加上人维护的离线标准。

评估先识别页面类型，再用六个共同维度评分，并按页面类型调整权重：

| 业务层 | 评估维度 |
| --- | --- |
| 业务语义 | Product Intent、Trust & Domain Fit |
| 用户任务 | Information Architecture、Interaction Readiness |
| 界面实现 | System Craft、Visual & Brand Expression |

每个维度继续分成 `subcheck`，使用 0–2 分。维度分由检查项聚合，最终总分再由运行时按页面类型权重计算。模型负责解释证据与质量影响，运行时负责算分和裁决，避免让一次模型输出同时承担观察、解释和最终放行。

证据来自四层：

1. DOM / CSS QA：溢出、裁切、低对比度、小点击目标、无可访问名称、坏图等确定性问题。
2. Page Profile：页面区块、导航、标题、CTA、真实路径、占位链接和可点击目标。
3. Click Smoke：关键点击是否产生错误、弹层、状态变化或完全没有反馈。
4. Screenshot：文字可读性、视觉层级、构图风险、品牌语气和动效目的。

DOM 说明页面里有什么，截图说明用户看到了什么，点击检查说明动作是否真的发生。确定性 QA 属于事实层，模型属于解释层，运行时属于裁决层。三者不能互相替代。

最后，交付闸门把分数、成熟度和阻断问题一起用于放行。过程稿、可演示原型和上线版本使用不同放行策略；主任务不清、关键路径断裂、领域逻辑错误、AI 回答无证据、缺少截图评审等问题不能被平均分抵消。未通过时，evaluator 要返回少量、带证据位置和责任归属的修改任务。

## 这套方法为什么成立

### 设计资产从参考资料变成运行时依赖

传统设计规范主要服务人类阅读。Agent 时代的规范还要满足可检索、可调度、可验证和可回流。Playbook 把设计专业从一次性交付物改造成生成系统依赖，后续每次生成都能复用同一套判断。

### 责任归属比更长的 Prompt 有效

当页面有问题时，系统需要知道应修正需求定义、业务语义、视觉事实源、组件语义、页面骨架，还是评估标准。问题能回到自己的真源，修正才会影响后续所有生成，而不是只修好眼前一张页面。

### 动态 UI 的关键是受控表达能力

开放式代码生成带来自由度，也带来一致性、安全、性能、可访问性和可验证性成本。纯文本足够安全，却难以承接复杂判断。A2UI 选择中间地带：Agent 生成语义，客户端拥有渲染权。

### 评分与放行被明确分开

平均分适合描述整体水平，不适合表达致命失败。阻断问题保护主任务、领域逻辑、可信度和关键交互，使局部视觉质量无法掩盖产品不可用。

## 需要保留的批判性判断

### 六份声明是责任模型，不应机械复制成六份文件

同一个团队可能已经用 PRD、schema、design tokens、组件文档、模板目录和 Profile 承担这些责任。再新增同名文件会制造重复事实源。应先映射现有资产与责任，只有确实存在空位时才新增载体。

声明之间还需要优先级和冲突规则。例如 `domain.md` 与 `design.md` 对状态色产生冲突时，应由业务语义先确定角色，再由视觉系统给出取值。Playbook 解释了分工，但没有完整定义跨声明冲突的解析机制。

### A2UI 示例只表达了方向，距离生产合同仍有距离

生产级 A2UI 至少还需要版本、schema 校验、消息与动作 ID、幂等、权限、超时、取消、重试、流式与局部更新、降级渲染、审计、provenance 和兼容策略。书中的 JSON 示例适合解释边界，不足以直接成为协议。

### 分数、权重和阈值需要真实样本校准

六维度模型提供了共同语言，但 7.5 / 8.0 阈值、页面类型权重和阻断清单仍是经验参数。长期有效性取决于好案例、坏案例、混合案例、边界案例和品类案例的离线校准，并需要持续观察误放行与误退回。

### 当前公开证据边界偏桌面 Web

正文明确描述默认 `1440x1000` 桌面视口，并禁止因为缺少移动端截图扣分。这让当前 evaluator 的边界清楚，同时也意味着它不能替代响应式、移动端、跨浏览器、键盘全路径、读屏器和真实数据链路验收。

### 设计词典解决表达问题，不直接提供 taste

12 类 188 个词条能把 kerning、semantic token、progressive disclosure、focus state 等概念翻译成规则，适合作为设计语言的基础索引。真正的判断还需要正反案例、对比样本、页面类型和业务目标。词汇表可以减少含混，无法单独决定什么是好。

## 对当前 workspace 的可复用映射

当前系统已经有 `Profile`、schema、quality gate、Workspace Memory、runtime references、Artifact provenance 和 browser acceptance 等正式合同。吸收 Playbook 时，应复用现有真源：

| Playbook 责任 | 当前系统优先映射 |
| --- | --- |
| `spec.md` | `Profile`、任务 schema、run contract、验收标准 |
| `domain.md` | 业务对象、状态机、稳定错误码、权限与 provenance 规则 |
| `craft.md` | UI / 文案 / 交互最佳实践与正反案例 |
| `design.md` | design tokens、主题、组件视觉状态与缺口登记 |
| `components` | 组件库 API、语义边界、允许状态和组合规则 |
| `template` | 页面类型、App Shell 与可复用任务骨架 |
| `skill` | 按任务触发和渐进加载能力，不重新定义任务合同 |
| `evaluator` | 浏览器证据、离线契约 E2E、阻断门禁与回流任务 |

这与当前仓库“任务合同只能有一个真源”“provenance 绑定持久化凭据”“浏览器证据不能被表面状态替代”的经验一致。新增设计能力时，优先增强现有合同，而不是挂载一份默认 skill 去覆盖 `Profile`。

对 Mindspace Workspace，最值得采用的是四条：

1. 让 `Profile` 继续独占目标、来源、产物和质量门禁；设计声明作为它引用的正交资产。
2. 把动态 UI 限制在上下文、风险或决策点确实变化的环节；稳定工作区、设置和长期信息架构继续使用固定 UI。
3. 让 Agent 输出结构化界面意图和动作，客户端保留组件、权限、本地化、可访问性与降级控制权。
4. 将 evaluator 的事实层、解释层和裁决层分开：真实页面与运行证据负责事实，模型负责判断，确定性程序负责 gate。

## 后续执行检查表

遇到 AI 生成 UI、GenUI 或 Agent Workspace 设计任务时，先回答：

- 任务合同的唯一真源是什么？
- 业务语义、视觉事实、组件语义和页面骨架分别由谁负责？
- 哪些界面必须稳定，哪些决策点确实需要运行时生成？
- Agent 输出的是语义合同，还是正在越权生成客户端实现？
- loading、empty、error、permission、timeout、cancel、retry 和 recovery 是否进入正式状态模型？
- 评估是否有真实 DOM、截图、交互、运行时和 provenance 证据？
- 分数之外，哪些问题必须阻断放行？
- 未通过结果能否回到明确真源，形成下一轮可执行任务？
- 新规则是否经过正反样本校准，是否减少误放行而没有扩大误退回？

## 最终结论

Vibe Designing Playbook 最值得继承的不是文件命名、固定权重或“Vibe Design”这个概念，而是一种工程边界：人的判断负责定义好，Agent 负责在明确合同内生成和解释，客户端负责受控渲染，浏览器与运行时提供证据，确定性门禁负责放行，人再用真实案例维护标准。

设计进入系统以后，核心资产从某一张稿，变成可引用的判断、清楚的责任边界和可复验的证据链。
