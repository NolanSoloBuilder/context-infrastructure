# 爱室丽选品 Agent：内部流程访谈底稿

日期：2026-09-18。状态：讨论与待核实流程，不是企业已确认 SOP，也不是已批准的 Demo 实施方案。

## 背景与证据边界

用户希望为爱室丽企业演示选品 AI Agent，当前先讨论内部选品流程。附图明确以「假设老板口述」开头，其中最近四个月新品转化低于竞品是示例命题，不能当成客户真实经营数据。用户尚未确认演示对象属于中国区商品团队、区域经销商还是总部研发采购。

公开资料能证明 Ashley 同时涉及制造、商品组合、零售伙伴和供货支持，中国官网存在零售门店与加盟入口；不能证明中国具体经营主体的采购权限、审批层级和数据系统。官方不同页面门店数字不一致，本底稿不采用门店数量。

- [零售合作说明](https://www.ashleyfurnitureindustriesllc.com/retailpartner/)说明商品组合、订货和商品资料支持；其美国库存及配送说明不能直接套用中国。

## 首先区分的决策层级

1. 总部产品开发/采购：决定开发或采购哪些产品，涉及供应商、打样、成本、质量与生产能力。
2. 中国区商品引进：决定哪些商品进入当地可售池，涉及本地客群、尺寸、价格、供应路径和交期；具体职责待确认。
3. 区域或门店经营：从可售池中决定上样、备货、订货和淘汰，受展位、现金、区域需求与补货条件限制。

不能默认将选品等同于 SKU 排序；选入可售池、上样、备货和订单采购是不同决策。

## 可供访谈校正的零售选品流程

以下责任角色和步骤均为行业工作假设，未获企业内部验证。

| 阶段 | 可能参与者 | 输入与关键判断 | 决策产物 |
| --- | --- | --- | --- |
| 经营复盘 | 商品、销售、门店、财务 | 按门店/渠道/上市时长看销售、毛利、库存与客户流失 | 待补品类、价格带或风格缺口 |
| 明确下一期目标 | 商品负责人、区域负责人 | 客群、空间户型、预算、展位、主推场景 | 选品约束与商品结构目标 |
| 建候选池 | 商品、采购、供应链 | 可选目录、新品、在售商品，属性和供应状态 | 候选清单及数据缺口 |
| 商业筛选 | 商品、财务、供应链 | 售价空间、成本、毛利、交期、最小订货量、售后风险 | 淘汰理由与入围理由 |
| 样品和搭配评审 | 门店、陈列、销售、商品 | 实物体验、尺寸、组合搭配、陈列空间、同类替代 | 拟上样组合与旧品退出方案 |
| 审批与订货 | 授权负责人、采购、财务 | 展样/库存资金、数量、风险与交付承诺 | 经批准的上样/采购计划 |
| 上市验证 | 门店、运营、商品 | 实际上样日期、曝光/到店、咨询/报价、成交、退货 | 保留、补货、调整、撤样建议 |

示例：某候选沙发本身受欢迎，但尺寸不适合当地户型，或与现有展示重复；另一款单品销量普通，却补齐某套客厅组合。这类取舍需要在商品组合与门店约束下讨论，不能仅按全公司销量排序。

## 从诊断进入选品的条件

若客户提出新品表现不佳，应先明确转化率分母：线上商品访客、线下到店、咨询或报价，均不是同一指标；新上架和真正上样/有货的时间也可能不同。外部竞品数据缺失时保留为待验证，不伪造基准。若差距来自供货交期或销售跟进，则下一步行动应调整履约或跟进，不能强行输出换品建议。

选品讨论可并列关注成交、毛利、库存占款、周转与展位产出，不预设一组看似精确的权重。不同职能之间的取舍与最终审批人需要访谈确认。

## 下一轮最有价值的输入

- 明确演示对象及其实际可决定事项。
- 选取最近一次真实选品案例：谁提出、候选从哪里来、谁筛掉哪些商品、依据什么、谁拍板、形成什么表单。
- 确认主力渠道，以及选品是新品引进、门店上样还是采购备货。
- 核对是否存在商品主数据、门店 SKU 销售、库存交期、客户咨询/流失原因；不预设内部系统名或接口可用性。

当前不实施 Agent，不连接企业系统，不将模拟数据当成真实业务证据。后续 Demo 应沿真实决策材料展示可追溯的候选、淘汰理由和需人工确认的取舍。

## 补充输入：市场扫描与商品匹配

用户追加聊天截图，并确认演示对象可能覆盖各层团队，要求标明差异。截图转述：对方已交流过，等待一份 brief；可以进一步与技术负责人等沟通现状，了解选品来源；设想 Agent 自动做市场调查与 mapping，例如按周关注市场新品、热度及社交媒体来源。截图属于需求线索，未授权定时任务、外部联络或实施。

「选品等等这是零」含义不明确，可能是数字化/自动化、体系化或某项具体能力不足，不可写成企业没有选品流程。每周一次是设想节奏，尚非确定需求。mapping 的对象也待确认：可以是外部商品到内部同款/相似款、属性到目标客群、趋势到品类缺口。

这条线索更接近选品上游的「市场扫描 → 信号归并 → 商品/需求画像 → 内部商品匹配 → 人工评审」；此前截图中的转化率诊断可作为另一条后续路径，不应成为当前 brief 的既定起点。

| 使用团队 | 同一外部信号可能触发的决策 | 需要追加的内部证据 |
| --- | --- | --- |
| 总部研发/采购 | 新品概念、打样或供应商调查 | 研发计划、成本工艺、质量标准、供应商与产能 |
| 中国区商品团队 | 引进候选、当地商品组合调整 | 全球可选目录、当地销售和户型、价格与到货条件 |
| 区域/门店 | 从获准可售池上样、替换陈列或备货 | 门店客群、现有样品、展位、库存、交期和订单 |

可用于讨论的端到端流程：明确市场和品类范围 → 从现有来源池收集信号 → 对转载/同款/营销内容归并并记录时间 → 提取尺寸、风格、功能、材质、价格和人群诉求 → 匹配内部商品与覆盖缺口 → 检查供应和商业约束 → 输出候选及拒绝理由供评审 → 跟踪小范围试样或其他验证结果。这是拟议流程，需拿真实历史案例与企业核对。

热度、需求、商业机会必须分开表达。互动量或社媒关注只能作为注意力信号，缺少同口径成交数据时不称为畅销。跨平台不直接相加点赞或播放量；记录观察窗口、平台、覆盖范围和样本偏差。缺少内部目录时只能输出外部机会候选，不编造内部 SKU 匹配、库存、毛利或采购建议。

示例仅为模拟：市场出现对小户型、可拆洗、适合宠物家庭的沙发讨论 → 归并成待验证需求 → 映射已有商品属性 → 说明匹配项和缺失信息 → 分别交给研发评估新品、商品团队评估引进、门店评估可售款上样。不得说成已发现爱室丽真实商品缺口。

下一次沟通应同时包含商品/买手或门店业务负责人和技术负责人：业务侧解释真实决策、否决条件与现有选品表，技术侧确认商品字段、数据来源、权限和读取方式。最有价值的起点是追踪最近一个实际被选中及一个被否决的商品，弄清来源、证据、审批和后续表现。

## Demo 底座建议（待确认）

按希望客户在浏览器试用、后续可能多人参与评审的假设，首选「独立部署 LibreChat + 自有选品工具服务」。若仅由演示者在自己的电脑现场操作，且不需要交付试用链接，则 Craft Agents 可作为更轻的首轮验证入口。用户尚未确认访问方式，本建议不等于已决定实施。

LibreChat 负责现成的 Web 交互与 Agent 工具编排；自有服务负责市场材料读取、证据记录、商品目录查询、匹配和报告产物。首期使用 LibreChat 自带 Agents 路径，不另行抽取其 SDK、自建 LangGraph 或同时接入另一套 Agent Loop。工具服务保留独立数据与 API 边界，后续可由 Craft/Goose 或 Cited Alpha 消费；不迁移 Cited Alpha 主产品。

Demo 可沿「输入选品 brief → 读取有出处的市场样本 → 提取需求/商品属性 → 查询内部商品 → 输出候选、依据和待确认项 → 用户修改约束后重新比较」完成一次交互。拟议工具可为 search_market_signals、get_product_catalog、compare_products、save_selection_brief；它们属于待实现接口，不是框架内置能力。不要用一个执行全部业务的黑盒工具掩盖数据和决策来源。

首期建议限定一个品类、一个市场和一批明确来源的商品样本；先按需触发，周度调度留待来源、时效和去重验证后实施。公开网页、企业授权导出和模拟目录必须标明不同性质。没有企业目录时只展示市场扫描，不能冒充完成真实内部匹配。

对其他候选的判断：MK Agent 已裁剪 Sources/MCP，当前场景需要外部信息与内部商品工具，补回成本需另估；Goose 适合定制桌面发行，但该 Demo 暂无本机操作或自有安装包要求；OpenHands 更偏研发任务；Dify 可作为明确固定流程后的备选，本阶段需求仍在发现中。不因框架支持工具就假设它能获取社媒全量数据或成交数据。

## 企业定制扩展路线（2026-09-18，建议）

判断：LibreChat 适合作为可定制的企业 Agent 入口，业务连接与 Agent 配置扩展较方便；复杂商品工作台、审批和业务状态仍需自建。开源可修改不等于存在稳定的任意前端页面插件接口。

| 层级 | 扩展方式 | 爱室丽例子 | 维护边界 |
| --- | --- | --- | --- |
| 部署配置 | YAML、环境配置、模型与界面开关、预设 Agent | 固定可用模型、欢迎语、品类研究指令 | 优先配置；完整品牌资源按实际入口修改 |
| 业务能力 | MCP 服务、工具 API、Skills | 市场证据读取、商品目录查询、属性比较、报告保存 | 自有服务持有数据与业务规则，避免写进 LibreChat 核心 |
| 身份与权限 | 企业 OIDC/SAML、角色/组、资源 ACL | 总部/区域/门店使用不同 Agent 或工具 | 应用资源权限不能替代业务 API 的行/字段级权限 |
| 业务界面 | 有界的 React 定制或独立业务页 | 商品对比表、候选池、来源面板、评审记录 | 自定义页面需要代码维护；不把生成式 Artifact 当成业务数据库或可信审批界面 |
| Agent 运行与运维 | 先复用内置循环，按需扩展宿主/SDK | 工具审批、异步研究、成本与失败跟踪 | 深改事件协议、数据模型和 Loop 会增加升级成本 |

权限示例：门店用户只能读取授权门店库存；采购成本是否可见由业务 API 根据可信身份校验。MCP 只负责调用协议，不能信任模型参数中的 userId/storeId，也不能把「不显示成本」的提示词当成字段权限。确认审批的业务记录、版本、执行状态和幂等键放在自有服务，不以聊天中的一句同意作为完整审批机制。

建议结构为企业 SSO → LibreChat 交互与 Agents → 经认证的选品 MCP/API → 市场证据库、商品目录、候选方案与评审记录。业务状态独立持久化，以实体 ID/版本与聊天关联；图片和来源必须携带实际对应商品及采集时间。接口可被未来其他 UI/宿主复用。

维护建议：一个共享 fork 加客户配置与连接器，首个企业可独立部署；客户之间分别部署不等于为每个客户维护不同代码分支。企业多租户 SaaS 需要单独验证数据库、检索、文件、日志和任务隔离，不能从多用户登录推导已经满足。保留上游 remote，锁定验收版本，小范围维护 UI diff，给关键适配接口做回归。

阶段建议：Demo 验证单品类市场信号到内部商品匹配；试点接真实目录、企业身份、数据范围和评审闭环；正式交付再落实调度、审计、失败恢复、备份、监控和升级。每阶段按真实业务要求收敛，不默认全部建设。

更新说明：官方目前已有 Scheduled Chats，但标为 experimental 且默认关闭，不能再将周度调度表述为必然从零开发。Agent Plugins 同样标为 experimental，主要打包 Skills、MCP 与 hooks，不等同于通用前端插件系统；多副本调度依赖共享 Redis 流，等待人工输入的计划任务还需要持久 checkpoint。正式采用须按锁定版本验证。
