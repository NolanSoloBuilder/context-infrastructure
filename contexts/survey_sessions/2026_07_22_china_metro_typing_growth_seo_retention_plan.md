# 中国地铁打字：传播、SEO 与复玩增长方案

日期：2026-07-22

关联项目：`adhoc_jobs/tw_metro_typing_china`

线上地址：<https://metro.forgepane.com>

## 一句话结论

下一阶段只建立一条增长链路：

> 搜索或社交内容带来玩家 → 完成当天统一挑战 → 获得有辨识度的成绩卡 → 邀请朋友挑战同一班车 → 查看个人最佳与当天名次 → 第二天回来刷新连续记录。

传播、SEO 和复玩不应各做一套功能。三者共用同一个原子对象：`DailyChallenge`。它有稳定 URL、确定题目、可比较成绩、可生成分享卡，也能成为每天回访的理由。

## 当前判断

项目已经覆盖 41 座城市、283 条线路和 6,155 条线路站点记录，单局游戏、移动端输入、地图、结果页和城市分享参数均已存在。当前瓶颈是：

- 页面只有一个 SPA 入口，城市仍主要通过 `?city=shanghai` 一类查询参数切换，搜索引擎缺少可独立理解的城市和线路页面。
- 结果页只有成绩与“重新选线 / 再跑一次”，完成之后没有可传播产物，也没有次日回访理由。
- 没有账户、历史记录、个人最佳、连续挑战和统一题目，因此玩家之间无法公平比较。
- 当前前端代码没有看到产品漏斗事件。传播、SEO 和留存优化缺少共同基线。
- 上游 `tw-metro-typing` 当前没有独立 License。商业推广或广告化前应取得书面授权，或者完成必要的独立实现替换。

已有 `2026_07_14_metro_typing_feature_gap_and_leaderboard_plan.md` 提议先做“每日挑战 + Google 登录 + 排行榜”。本方案保留每日挑战和公平榜单，调整实施顺序：首版不要求登录，先用本地匿名身份验证复玩和分享；只有出现明确跨设备保存需求后，再选择符合中国用户习惯的账户方案。

## 增长对象与 URL 合同

### 1. 每日挑战 `DailyChallenge`

每天固定以下字段：

- 日期与时区：`Asia/Shanghai`
- 城市、线路、区间、方向
- 30 秒统一时长
- 输入方式：简体中文与拼音分别计分
- 数据版本与规则版本
- 可重复计算的 challenge ID

生成规则使用版本化确定性 seed，但只从经过数据审计、长度合适的线路白名单中选题；同一线路 30 天内不重复。规则版本变化时保留历史挑战的可回放能力。

### 2. 稳定 URL

建议最终 URL：

```text
/                         游戏首页
/daily                    自动进入今日挑战
/daily/2026-07-22         某日挑战与当日榜单
/city/shanghai            上海地铁打字练习入口
/city/shanghai/line/1     上海地铁 1 号线练习页
/leaderboard/daily/2026-07-22
/how-to-play
/about
/data-sources
/privacy
```

社交分享链接指向具体挑战，不直接指向首页：

```text
/daily/2026-07-22?ref=匿名分享码
```

`ref` 只用于归因，不携带昵称、成绩或设备标识。

## 传播方案

### 传播触发点

传播动作只出现在结果页。游戏开始前和输入过程中保持专注，不使用弹窗、浮层或强制分享。

结果页新增三个层级：

1. **成绩结论**：完成站数、速度、正确率、个人最佳差值。
2. **比较语义**：今日暂列第 N 名或超过 N% 玩家；样本不足时直接显示“今日第 N 位完成挑战的玩家”，不制造虚假百分位。
3. **下一步**：主按钮“挑战同一班车”，次按钮“再跑一次”，弱入口“查看今日榜”。

### 分享卡

卡片的价值是让未访问网站的人也能看懂挑战：

```text
上海地铁 1 号线 · 今日挑战
30 秒通过 7 站
平均 42 字/分钟 · 正确率 96%
超过今日 78% 的玩家

你能赶上这班车吗？
二维码 / 挑战链接
```

需要两种尺寸：

- `1080 × 1440`：小红书、朋友圈图片。
- `1200 × 630`：链接的 Open Graph 预览图。

移动端优先调用 Web Share API；不支持时提供“保存成绩卡”和“复制挑战链接”。分享成功只能由浏览器可确认的结果记录，点击分享按钮不算成功。

### 社交内容主题

社交传播分为两条内容线：

**面向普通玩家**

- `上海人能在 30 秒打到几站？`
- `用你每天坐的地铁线测手速`
- `全国 41 城，哪条线路最难打？`
- `莘庄、莘桥、莘塍：地铁站名里的多音字挑战`

**Build in public**

- 为什么把全国地铁线路做成打字游戏。
- 地铁支线合并、站名纠音和数据审计中的真实问题。
- 移动端软键盘如何改变地图镜头。
- 每日挑战上线后的真实开始率、完成率和复玩率。

普通玩家内容负责拉新，Build in public 负责积累个人品牌和产品可信度。每次只展示一个可验证变化或一个真实挑战，不发布泛化的开发流水账。

### 第一轮传播实验

只选一个城市做首轮：上海。

1. 发布“上海 1 号线 30 秒挑战”短录屏。
2. 评论区只问“你每天坐哪条线”，用回答决定下一条内容，不要求机械点赞收藏。
3. 第二篇发布互动最高的线路挑战。
4. 第三篇公开第一轮数据：访问、开始、完成、分享和复玩。

同一入口连续验证三次之后，再扩展北京、广州、深圳、成都等城市，避免 41 城同时铺开导致内容无法比较。

## SEO 方案

### SEO 的页面原子

首批只建设三类真实页面：

| 页面 | 用户意图 | 页面必须提供的真实价值 |
| --- | --- | --- |
| 首页 | 中国地铁打字游戏 | 产品说明、城市入口、今日挑战、玩法 |
| 城市页 | 上海地铁打字 / 上海地铁站名练习 | 线路列表、城市线路图、推荐挑战、数据更新时间 |
| 线路页 | 上海地铁 1 号线站名 / 拼音练习 | 完整站名、起终点、方向、地图、易错读音、立即练习 |

不要首批生成 6,155 个车站页面。单站页面缺少独立任务和原创信息，容易形成大量薄内容。先发布 5 个城市页和每城 3–5 条真实线路页，观察 Search Console 查询后再扩展。

### 内容要求

城市页和线路页不能只替换城市名。每页至少包含：

- 从真实数据生成的线路和站点信息。
- 直接可玩的该城市或该线路挑战。
- 数据更新时间、来源和非官方声明。
- 经人工核对的多音字、易错站名或线路变化说明。
- 指向相邻线路、城市页和玩法说明的正常 `<a href>` 链接。

Google 当前明确强调 people-first、原创、可靠内容，并反对为覆盖查询变体而批量生成缺少增量价值的页面。因此 SEO 内容应来自这个项目真正做过的数据审计、纠音和游戏体验，而不是批量生成地铁百科。

### 技术实现

不需要为了 SEO 立即迁移到 Next.js。保持 Vite + React 游戏，新增构建时静态生成层：

1. 从 `public/data/metro.json` 生成首批城市和线路 HTML。
2. 每个 URL 输出独立的 `<title>`、description、canonical、Open Graph 和可见正文。
3. 使用真实 `<a href>` 建立城市、线路和玩法页面之间的内部链接。
4. 根目录生成 `robots.txt` 和 `sitemap.xml`，sitemap 只包含 canonical URL。
5. Cloudflare Worker 对 SPA 路由返回对应 HTML shell，避免所有 URL 都落到同一份首页元数据。
6. 在 Google Search Console 验证站点，提交 sitemap，并用 URL Inspection 检查渲染结果。
7. 接入百度搜索资源平台时使用同一 sitemap；先实测抓取与中国大陆访问质量，再决定是否需要迁移静态资源或底图。

Google 对 JavaScript 站点建议为不同内容提供独立 URL，通过 History API 管理客户端路由，并使用可抓取的 `<a href>` 链接。静态生成能进一步减少渲染差异。XML sitemap 应放在根目录并使用完整 canonical URL。

### 结构化数据

第一阶段只使用与可见内容一致的基础类型：

- 首页：`WebSite`、`WebApplication`。
- 城市和线路页：`BreadcrumbList`。

不要虚构评分。Google 的 SoftwareApplication 富结果要求价格以及真实评分或评论之一；没有真实用户评价时，不以获取富结果为目标。任何 JSON-LD 字段都必须在页面正文中有对应内容。

### 首批页面

建议先发布：

- `/city/shanghai`
- `/city/beijing`
- `/city/guangzhou`
- `/city/shenzhen`
- `/city/chengdu`
- 每个城市选择 3 条认知度高、数据已完成审计的线路页
- `/daily`
- `/how-to-play`
- `/data-sources`
- `/about`

第一批约 20 个 URL，足够验证收录和搜索意图，无需批量铺站点页。

## 复玩机制

### P0：无账号复玩

先在本地完成以下能力：

- 今日挑战。
- 本机个人最佳。
- 连续挑战天数。
- 最近 7 天完成记录。
- 结果页显示“比个人最佳多 / 少 N 站”。
- 第二天首次访问时显示昨天成绩与今日挑战入口。

这些数据使用版本化 localStorage 保存。存储失败时仍允许开玩，界面明确降级为“不保存本机记录”。

### P1：匿名日榜

当复玩指标达到首轮门槛，再加入 Cloudflare Worker + D1：

- 服务端生成一次性开局 nonce。
- 玩家首次提交成绩时选择昵称，浏览器生成匿名设备密钥。
- 每日挑战、中文和拼音分别计榜。
- 榜单只保存最佳成绩，显示昵称，不收集邮箱。
- 分数由服务端根据挑战版本、时间和输入摘要重算。

匿名身份只能承担低风险游戏成绩。需要更换设备、找回记录或参与长期好友榜时，再询问用户是否愿意登录。

### P2：持续目标

只有日榜和复玩已经被验证后，再增加：

- 周榜与城市榜。
- 线路个人最佳。
- 城市护照：完成一条线路点亮一枚章。
- 每周任务：完成三个不同城市或三种线路长度。
- 好友挑战历史。

暂不做全国长期总榜、学校榜、实时对战和复杂成就系统。这些功能需要反作弊、身份和运营成本，无法帮助首轮验证。

## 数据与实验

### 北极星指标

`每周跨至少两个自然日完成挑战的玩家数`

它同时要求用户完成游戏并产生复访，比注册数、PV 或单次开始数更接近真实留存。

### 事件合同

```text
page_view
city_page_view
line_page_view
daily_challenge_view
game_start
game_complete
result_view
retry_start
share_open
share_success
referral_landing
leaderboard_view
streak_updated
```

每个事件只携带必要字段：`city`、`line_id`、`mode`、`challenge_id`、`device_class`、`referrer_type`。不记录输入内容、剪贴板、精确位置或个人身份。

### 首轮实验门槛

这些数值是产品继续投入的门槛，不是行业基准：

| 指标 | 首轮门槛 |
| --- | ---: |
| 访问首页或挑战页后开始游戏 | ≥ 35% |
| 开始 30 秒挑战后完成 | ≥ 65% |
| 结果页点击“再跑一次” | ≥ 20% |
| 结果页发起分享 | ≥ 5% |
| 分享落地页进入游戏 | ≥ 20% |
| 次日回访 | ≥ 12% |
| 7 日内至少两天完成挑战 | ≥ 8% |

如果分享率低，先检查成绩卡是否值得展示；如果分享落地后的开始率低，检查链接是否直接进入同一挑战；如果复玩低，先检查每日挑战是否足够有变化和比较价值。不要用增加通知、登录墙或更多模式掩盖核心循环的问题。

## 六周实施顺序

### 第 1 周：建立基线与授权边界

- 确认上游代码商业使用授权。
- 接入匿名事件和 Cloudflare Web Analytics。
- 固化事件字段、隐私说明和基线仪表盘。
- 保持现有游戏体验不变，采集一周自然数据。

### 第 2 周：SEO 技术底座

- 建立路径路由、canonical、动态 title/description。
- 发布 `robots.txt`、`sitemap.xml`、Search Console。
- 静态生成首批 5 个城市页和玩法、数据来源页。
- 验证 Googlebot 渲染和移动端 Core Web Vitals。

### 第 3 周：每日挑战与本地复玩

- 上线版本化 `DailyChallenge`。
- 增加本机个人最佳、连续天数和最近 7 天记录。
- 结果页加入个人最佳差值和今日再战入口。

### 第 4 周：分享闭环

- 生成 1080 × 1440 成绩卡。
- 接入 Web Share、保存图片和复制链接 fallback。
- `/daily/YYYY-MM-DD` 返回对应 Open Graph 元数据。
- 发布上海首轮三篇内容实验。

### 第 5 周：线路 SEO 页面

- 为首批 5 城各发布 3 条线路页。
- 加入真实站名、地图、纠音说明、数据来源和练习入口。
- 根据 Search Console 查询补标题与内部链接，不批量扩页。

### 第 6 周：根据数据决定是否上榜

- 达到复玩门槛：实现匿名 D1 日榜和一次性 run session。
- 复玩达标但分享低：先优化成绩叙事与挑战链接。
- 搜索有曝光但开始率低：优化城市/线路页到游戏的入口。
- 三条路径都没有达到门槛：停止扩功能，重新判断受众与核心挑战。

## 第一版范围

第一版建议只交付：

1. 匿名事件。
2. 5 个城市 SEO 页与 15 个线路页。
3. 每日 30 秒挑战。
4. 本机个人最佳和连续天数。
5. 结果页成绩卡与同题挑战链接。
6. Google Search Console、sitemap 和基础索引监控。

暂缓登录、全国榜、学校榜、好友系统、车站收集、更多玩法和广告。先验证“有人愿意开始、完成、分享、第二天再来”这四件事，再决定产品是否值得进入运营与商业化阶段。

## 2026-07-22 本地实现记录

本轮按“先本地验证、不发布”执行，未调用 Cloudflare、GitHub 或任何线上部署能力。

已完成：

- 建立 `/daily`、`/daily/YYYY-MM-DD`、`/city/:city`、`/city/:city/line/:line` 的客户端路径合同和独立页面元数据。
- 每日挑战以 `Asia/Shanghai` 日期、数据版本和规则版本生成确定性题目；固定城市、线路、区间、方向和 30 秒时长。
- 本机记录使用版本化 localStorage，支持中文/拼音分别保存个人最佳和连续挑战天数；存储不可用时明确降级。
- 结果页增加本机最佳、连续天数与“挑战同一班车”；优先使用 Web Share，不支持时复制挑战文案与链接。
- 产品事件仅写入当前浏览器 sessionStorage，并派发页面内事件，不向任何第三方发送数据。
- 构建时静态生成上海、北京、广州、深圳、成都 5 个城市页、每城 3 个编号线路页，以及当天挑战页；同时生成 `robots.txt` 和只包含 canonical URL 的 `sitemap.xml`。
- 城市和线路页包含真实线路/站点正文、普通 `<a href>` 内链、数据来源说明与非官方声明。

本地验证结果：

- `pnpm test`：53 项通过。
- `pnpm build`：通过；构建产物包含 21 个独立 SEO 页面，sitemap 共 22 个 URL（含首页）。
- Chrome 桌面与 `390 × 844` 手机尺寸完成 `/daily → 开始 → 30 秒自然结束 → 本机记录结果` 验证。
- Chrome 验证城市/线路内容页、独立标题、移动端布局与可访问名称；未发现来自应用代码的浏览器错误。

仍未实现且不应被视为已发布范围：动态分享图片、云端统计、Search Console、匿名排行榜、登录和任何广告接入。上游代码授权边界仍需在商业化或推广前解决。
