# App Store 榜单到 Web niche 的执行计划

日期：2026-07-17  
模式：Internal decision memo

## 结论

这条路径可以做，但 App Store 排名只能作为需求发现入口，不能作为 Web 产品成立的证据。移动 App 排名混合了 Apple 分发、广告投放、品牌导流、季节性和原生能力依赖。真正的机会来自一个更窄的交集：App 已经证明用户会主动完成某项任务；该任务在桌面浏览器里更自然；浏览器能在一次 session 内完成主要计算；用户还会在 Google、Reddit、YouTube 或专业社区里独立寻找解决方案。

目标不是把某个固定排名区间的 App 逐个 Web 化，而是用榜单批量发现任务，再筛出适合 `local-first web tool` 的垂直问题。第一轮建议只研究美国 iPhone 市场，排除游戏和大型内容平台，集中在 Productivity、Photo & Video、Utilities、Graphics & Design、Education、Health & Fitness、Business、Music、Reference 九类。

## 数据边界

Apple 公开 RSS 目前最多实际返回 100 条。要覆盖更完整的榜单、分类、历史变化和上升趋势，需要购买或试用榜单数据服务。优先顺序：

1. AppTweak Top Charts API：公开文档称当前榜单可返回最多 500 个应用，支持 `limit` 和 `offset`，适合做分层采样。
2. Appfigures Public Data API：支持当前 snapshot、分页、分类和国家，文档给出的默认深度为 400，适合补历史 rank、评论和元数据。
3. Apple RSS：保留为零成本校验源，用于前 100 名和多国家横向验证，不能承担主数据源。

不要逆向 App Store 私有接口作为长期数据基础。接口漂移和使用条款风险会持续消耗维护时间。第一轮先手工导出或买一个月 API credits，等筛选框架证明有价值后再自动化。

## 分层候选池

每天采集以下榜单，连续保留 30 天：

- 美国总榜：Free、Paid、Grossing 的可获得完整榜单，至少覆盖前 500 名。
- 九个目标分类：Free、Paid、Grossing 的可获得完整榜单。
- 可选对照市场：英国、加拿大、澳大利亚，只记录在两个以上英语市场同时出现的候选。

采集后按四层研究，而不是平均处理所有 App：

| 层级 | 排名与状态 | 主要价值 | 主要风险 |
|---|---|---|---|
| A | 总榜或分类榜 1–50 | 需求和付费已经得到较强验证 | 品牌、投放和竞争通常最强 |
| B | 51–200 | 需求、竞争和开发规模相对平衡 | 仍可能依赖买量或短期热点 |
| C | 201–500 | 更容易发现垂直职业和低竞争任务 | 需求规模和付费能力需要额外验证 |
| D | 新上榜、快速上升、跨市场重复出现 | 发现正在形成的新任务和新产品形态 | 波动大，容易把投放当成需求 |

每层先选 20–30 个任务型 App，保证候选池既包含已验证的大需求，也包含竞争较弱的小需求。优先级由最终评分决定，不由排名高低决定。

每条记录至少保存 `app_id`、榜单、国家、分类、rank、日期、价格、IAP、评分、评分数、最近更新时间、开发者、App Store URL。按 `app_id` 去重后，预期第一周会得到 500–1,500 个候选。

榜单位置的使用方式：同时看 7 日中位排名、30 日出现天数、排名斜率、跨国家重复度和 Free / Paid / Grossing 之间的关系，不看单日截图。突然冲榜的 App 经常来自投放或热点，并不能代表长期需求。

## 四道筛选门槛

### 1. 浏览器可完成

优先选择输入和输出边界清楚的任务：用户拖入文件、粘贴文本、录音或填写少量字段，浏览器处理后导出结果。适合的能力包括 Canvas、Web Audio、WebCodecs、WASM、WebGPU、File System Access、OPFS、Web Workers、PWA 和本地模型。

直接排除：HealthKit、持续 GPS、CallKit、系统 VPN、完整通讯录、后台蓝牙、CarPlay、Widget、Apple Watch、持续推送、跨 App 自动化和依赖 iOS Share Sheet 的核心任务。需要用户安装扩展才能成立的产品单独进入 `Chrome extension` 赛道，不与纯网站混评。

### 2. Web 使用场景更自然

至少命中两项：

- 输入文件本来就在电脑上；
- 需要批量处理；
- 需要大屏对比、编辑或导出；
- 用户临时使用，不愿安装；
- 数据敏感，本地处理能形成明确卖点；
- 用户需要跨平台分享结果；
- 任务有明确的搜索查询，如 `compress x for y`、`convert a to b`、`remove c from d`。

### 3. 存在独立需求

App 排名之外，至少找到两类证据：

- Google 搜索结果存在专门工具页，且不是全被 Adobe、Canva 等平台垄断；
- App Store 一至三星评论反复描述同一个失败任务、价格抱怨或隐私担忧；
- Reddit、YouTube、行业论坛出现具体操作求助；
- 竞品存在明确收费、IAP 或订阅；
- 关键词有商业意图，而不是纯知识查询。

### 4. 一个人可以经营

两周内能交付核心任务；不依赖人工运营内容；不需要双边市场；没有高频版权投诉；不碰诊断、投资建议、身份验证等高责任结论；每月第三方 API 成本能随收入线性增长，或主要计算可以留在客户端。

## 评分卡

满分 100，低于 70 不进入验证：

| 维度 | 权重 | 判定依据 |
|---|---:|---|
| 独立搜索与社区需求 | 20 | 搜索意图、SERP、论坛求助、趋势稳定性 |
| Web 体验优势 | 15 | 桌面、批量、免安装、分享、跨平台 |
| 技术可行性 | 15 | Browser API 覆盖、性能、文件大小、fallback |
| 付费证据 | 15 | 订阅/IAP、付费榜、评论中的价格信号 |
| 竞争空隙 | 15 | 现有 Web 工具的缺口、垂直工作流差异 |
| 获客可行性 | 10 | SEO 长尾、模板页、社区或专业渠道 |
| 两周交付与维护 | 5 | 开发范围、第三方依赖、support 负担 |
| 风险 | 5 | 隐私、版权、医疗/金融责任、滥用风险 |

排名不单独计分。它用于候选发现和分层，并通过持续时间、上升速度、跨市场重复度帮助判断信号强弱，避免把“榜单位置”重复算成需求和付费证据。

## Chrome 技术策略

产品默认采用纯 Web / PWA，计算顺序是：

1. 浏览器原生 API；
2. WASM / WebGPU 本地推理；
3. 用户设备不支持或任务过重时，显式切换云端；
4. 账号、支付、同步和极少量队列任务放在薄后端。

Chrome Prompt API 可以用于文本抽取、分类、改写和小规模多模态任务，但不能成为唯一 runtime。当前官方文档仍列出桌面系统、内存、GPU、磁盘和模型下载要求，移动 Chrome 也没有同等覆盖。生产实现应做 capability detection，并准备 Transformers.js / ONNX Runtime Web、WASM 或云模型 fallback。真正的卖点写成“文件默认留在本机”或“无上传模式”，不要把 `Chrome built-in AI` 当成用户价值本身。

## 30 天执行节奏

### 第 1 周：建立候选池

- 选定 AppTweak 或 Appfigures，导出美国总榜和目标分类可获得的完整榜单，至少覆盖前 500 名。
- 建一个可重复运行的 collector，保存每日 snapshot，不急着做 dashboard。
- 分别从 A/B/C/D 四层抽样，用元数据和 App 描述进行第一轮规则过滤，留下约 100–150 个任务型 App。
- 人工检查每层至少 10 个，校准“原生依赖”“Web 更自然”“垂直任务”标签，避免筛选器只偏向高排名产品。

交付物：原始 snapshot、去重候选表、标签定义、30 个已人工复核样本。

### 第 2 周：从 App 名称转成用户任务

- 每个候选读取 App 描述、IAP、最近更新、近 100 条评论。
- 把产品名改写成原子任务，例如“扫描仪”要继续分成合同去阴影、收据表格提取、身份证件打码、批量 OCR。
- 搜索对应的 Google query、Reddit 求助和现有 Web 工具。
- 按评分卡选出 10 个候选，再写 3 个一页式 opportunity brief。

每份 brief 必须包含：目标用户、触发场景、输入、输出、当前替代方案、Web 优势、价格锚点、分发入口、两周 MVP、淘汰理由。

### 第 3 周：做三个任务级原型

- 每个候选最多投入两天，只实现最关键的输入到输出路径。
- 用真实大小的文件做性能测试；记录首次模型下载、峰值内存、处理耗时、浏览器兼容和失败率。
- 找 5–10 名真实目标用户完成任务。观察他们能否在没有讲解的情况下产出可用结果。
- 只把完成率最高、痛点最具体的一个升级为可公开使用的工具。

### 第 4 周：上线一个工具，测试三个需求入口

- 上线一个完整工具，同时为另外两个候选保留真实、具体的 landing page 和等待名单。
- 为主工具制作 5–20 个高意图页面，页面由真实任务差异产生，不批量生成近义词 SEO 页。
- 接入匿名事件：进入工具、选择输入、开始处理、成功导出、失败原因、二次使用、付费意图。
- 去目标用户已经出现的社区做问题回答和工具演示；避免无上下文投放链接。

## 继续与淘汰标准

原型阶段满足以下条件才继续：

- 真实用户任务完成率至少 60%；
- 进入工具后的核心操作启动率至少 25%；
- 至少 5 名用户明确表示现有方案的具体问题，不能只说“挺方便”；
- 本地处理在目标设备上的 P75 时间可接受，且失败能自动 fallback；
- 竞品收费或用户有明确付费行为；
- 获客入口能够写成具体 query 或定位到具体社区。

上线后用 30–60 天观察自然流量。若获得 300 个高意图访客后，核心操作启动率仍低于 15%，或完成任务后没有任何保存、分享、再次使用、付费意图，则停止。SEO 没有获得曝光时，先判断关键词和收录问题，不把低流量误判成产品体验失败。

## 优先研究的任务形态

第一轮关注形态，不先押具体产品：

1. 专业文件处理：面向某种职业或交付规范的 PDF、图片、音频、表格转换、校验、打码和批处理。
2. 隐私型本地 AI：会议、客户材料、合同、病例之外的低责任敏感文本，强调默认不上传。
3. 创作者生产步骤：一个明确平台或格式的字幕、裁切、降噪、章节、封面、元数据和导出检查。
4. 垂直分析器：输入一个文件或 URL，输出可核对的检查结果，而不是泛化 AI 助手。
5. 专业计算器与生成器：规则足够复杂、结果可以立即导出或交付，并且规则来源可维护。

暂时避开通用图片压缩、通用 PDF 合并、通用转录、通用 AI 写作和聊天壳。这些任务技术上最容易，SERP 和品牌竞争也最密集。更好的切入点是“某类用户在某个交付节点必须得到某种格式”，产品页面直接围绕该工作结果组织。

## 第一项实际动作

购买或试用一个月 AppTweak / Appfigures 数据访问，先拉取 2026-07-17 当天美国总榜与九个目标分类的 Free、Paid、Grossing 榜单，尽量覆盖前 500 名。只要能得到 `rank + app_id + chart + category`，其余描述、评分和开发者信息可以再用 Apple 公开元数据补全。随后按 A/B/C/D 四层抽样，用本文件的门槛和评分卡产出第一版 Top 20，而不是先做正式网站。
