# 用户数据来源

## Gmail 可抓取信息列表

### 一、基础标识信息

- ✅ message_id - Gmail 消息唯一 ID
- ✅ thread_id - 邮件线程 ID（用于关联同一对话）
- ✅ history_id - Gmail 历史记录 ID（用于增量同步）
- ✅ internal_date - 内部日期（Unix 时间戳）

### 二、邮件内容

- ✅ snippet - Gmail 自动生成的预览片段
- ✅ body_text - 纯文本正文（从 text/plain 部分提取）
- ✅ body_html - HTML 格式正文（从 text/html 部分提取）
- ✅ title - 邮件主题（从 Subject 头获取）

### 三、邮件头信息（Headers）

- ✅ From - 发件人
- ✅ Subject - 主题
- ✅ To - 收件人
- ✅ Date - 邮件日期
- ✅ List-ID - 邮件列表 ID（用于识别邮件列表）
- ✅ List-Unsubscribe - 退订链接头

### 四、标签和分类

- ✅ label_ids - Gmail 标签 ID 列表（如 ["INBOX", "CATEGORY_UPDATES", "CATEGORY_PROMOTIONS"]）

### 五、退订信息

- ✅ unsubscribe_links - 退订链接列表（从 List-Unsubscribe 头解析）

### 六、元数据

- ✅ fetched_at - 数据获取时间
- ✅ event_ts - 邮件事件时间（从 Date 头或 internalDate 解析）

## Twitter 可抓取信息列表

### 一、基础标识信息

- ✅ id - 推文唯一 ID（数字字符串）
- ✅ author_id - 作者用户 ID（用于关联用户信息）

### 二、推文内容

- ✅ text - 推文文本内容
- ✅ lang - 推文语言代码（如 zh, en）

### 三、时间信息

- ✅ created_at - 推文发布时间（ISO 8601 格式，如 2024-01-15T10:30:00.000Z）

### 四、互动指标（Public Metrics）

- ✅ public_metrics - 公开互动指标对象，包含：
- retweet_count - 转发数
- like_count - 点赞数
- reply_count - 回复数
- quote_count - 引用数

## Notion 可抓取信息列表

### 一、基础标识信息

- ✅ id - 资源唯一 ID（页面或数据库）
- ✅ object - 资源类型（"page" 或 "database"）

### 二、内容信息

- ✅ title - 标题
- 页面：从 properties.Name.title 提取
- 数据库：从 title 数组提取
- ✅ content_text - 内容文本（仅页面，可选）
- 从页面块（blocks）中提取所有 rich_text.plain_text
- 需要 include_page_content=true 才会获取
- 从 content.results 中递归提取所有文本块

### 三、页面内容（Content，仅页面，可选）

- ✅ content - 页面块内容对象（需要 include_page_content=true），包含：
- results - 块列表，每个块包含：
- type - 块类型（如 paragraph, heading_1, bulleted_list_item）
- {type}.rich_text - 富文本数组，每个元素包含：
- plain_text - 纯文本内容

# 产生用户画像的逻辑

## 用户画像生成逻辑

### 一、整体流程概览

数据采集 → 内容入库 → 标签生成 → 标签聚合 → LLM画像生成 → 画像持久化

### 二、详细流程

#### 阶段 1：数据采集与入库

数据来源：

- Gmail：邮件（主题、正文、发件人等）
- Twitter：推文（文本、互动数据、媒体等）
- Notion：页面/数据库（标题、内容、状态等）

处理：

- 转换为统一格式存入 UserContent 表
- 原始数据存入 RawSourcePayload 表

关键字段：

- content_text：内容文本

\- Twitter：推文的完整文本内容

\- Gmail：邮件正文纯文本（优先），如果没有则使用 Gmail 预览片段，最后使用邮件主题

\- Notion：如果获取了页面内容则为所有文本块的组合，否则为页面标题

- event_ts：事件时间
- source：数据源（gmail/twitter/notion）

#### 阶段 2：标签生成（ContentTaggingService）

触发时机：

- 内容入库后自动触发

处理流程：

1. 文档准备

- 从 UserContent 表读取文档
- 提取 content_text、title、source 等信息

1. LLM 标签提取

- 使用 LLM（如 GPT-4）分析文档内容
- 生成 4-8 个结构化标签

1. 标签类型（\_ALLOWED_TAG_TYPES）：

- topic：主题
- interest：兴趣
- sentiment：情感（positive/neutral/negative）
- entity：实体
- action：行为
- intent：意图

1. 标签元数据（这个就是AI根据内容产出的数据，十条推特内容合并生成，两片gmail邮件合并生成，notion每一页生成）：

```JSON
  {
     "type": "topic",
     "value": "AI 技术",
     "confidence": 0.85,
     "metadata": {
       "summary": "简要说明（≤18词）",
       "keywords": ["关键词1", "关键词2"],
       "evidence": "证据片段（≤12词）",
       "attributes": {
         "tone": "informational",
         "intent": "share knowledge"
       }
     }
   }
```

1. 标签存储

- 保存到 UserContentTag 表
- 包含：tag_type、tag_value、confidence、meta（元数据）

#### 阶段 3：标签聚合（UserSignalAggregator）

功能：收集并汇总用户的所有标签，为画像生成准备数据处理流程：

1. 标签收集（collect_user_snapshot）

- 从 UserContentTag 表查询用户的所有标签
- 支持过滤：
- tag_types：按标签类型过滤
- source：按数据源过滤
- min_confidence：最小置信度阈值（默认 0.0）
- 限制：
- limit_total：总标签数上限（默认 400）
- max_tags_per_type：每种类型上限（默认 200）

1. 标签聚合统计（\_aggregate_tags）

- 按标签类型分组
- 对每个标签值统计：
- count：出现次数
- avg_confidence：平均置信度
- latest_ts：最新出现时间
- latest_evidence：最新证据文档 ID
- 按置信度和出现次数排序，取 Top 10

#### 阶段 4：LLM 画像生成（UserProfileService）

功能：基于标签tag快照，使用 LLM 生成结构化用户画像

System prompt：

```Plain Text
  You are an expert persona analyst. Using only the supplied user signals, produce a structured JSON profile describing the user's professional function, industry domain, interests, forward-looking intents, and likely information sources. Use the tag data provided as context, leave any field empty when signals are insufficient, and output as many distinct entries as the evidence supports. Do not limit yourself to predefined taxonomies—choose the most specific descriptors possible.
```

# 卡片数据生成

- 邮件卡片
- 数据源：UserContent 中最近 24 小时内的 Gmail 文档（已入库的邮件内容）。
- 获取方式：按时间倒序取 N 封（默认 10）→ 在应用层进行分块或直连汇总→ 调用 LLM 生成 Markdown 摘要卡片。

system prompt：

```Plain Text
system_prompt = (
    "You are an executive assistant who analyses recent emails to surface the most critical information for the user.",
    {guidelines},
    {instructions.get("style")},
)

 这里的guidelines和style可修改：
"guidelines": [
        "Write a Gmail digest that lets the user grasp every message without opening their inbox.",
        "Begin with a short overview paragraph that captures the general theme of the inbox.",
        "For each email, add a heading in the format `### Subject — Sender (HH:MM)` and add 2–3 bullet points covering gist, key info, and any requests.",
        "Call out deadlines, next actions, and owners in bold. If multiple emails share the same thread, merge them under one heading in chronological order.",
        "Finish with a `## Follow-ups` section listing outstanding actions with due dates; write `None` if there are no follow-ups.",
],
"style": "Be concise, use bullet lists, and never invent information.",
```

User  prompt:

```Plain Text
user_message = (
    "Review the following emails and produce the digest requested in the system instructions.\n\n"
    f"{email_body}"
)

这里面的email_body包含了：
  - Email n: 标识顺序；
  - Mail ID:（若有）；
  - Subject: 没有主题时写 (No subject)；
  - Sender: / Received: 等基本信息（存在才写）；
  - Snippet: 邮件摘要（存在才写）；
  - Body: 会直接放正文文本；
  - Attachments: 若有附件描述也会列出。
```

- 可用来源（providers）：cloudsway（网页/新闻/垂直源聚合），twitter（社交内容）。
- 检索执行：分别调用
- cloudsway_search_service：统一网页搜索接口（标准化标题、摘要、URL、发布时间、来源作者等）。

- 卡片生成：每条查询对应一组检索结果（最多传入 8 条）→ LLM 生成 1 张“画像文章卡片”（含引用来源 sources，以及用于追溯的 search_results）。

- 所有检索结果在进入 LLM 前均被标准化为统一结构（provider/query/title/summary/url/published_at/author/raw），保证不同来源的一致性可用。

Your D‑U‑N‑S Number will be used to check the identity and legal entity status of your organization as part of our enrollment verification process for joining the Apple Developer Program or the Apple Developer Enterprise Program. While many types of businesses can receive a D‑U‑N‑S Number, your business must be recognized as a legal entity (such as a corporation, limited partnership, or limited liability company) to enter into the legal terms and obligations of Apple Developer Program agreements. DBAs, fictitious businesses, trade names, and branches are not accepted.    Companies and educational institutions must provide a D‑U‑N‑S Number registered to their legal entity. A D‑U‑N‑S Number is optional for government organizations. If you’re enrolling as an individual, you don’t need a D‑U‑N‑S Number.    Requesting a D‑U‑N‑S Number    D&B may have already assigned your organization a free D‑U‑N‑S Number. Before enrolling, look up your organization to see if you have a D‑U‑N‑S Number.
