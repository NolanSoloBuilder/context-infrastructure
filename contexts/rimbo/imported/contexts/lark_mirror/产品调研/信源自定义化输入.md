# 自有信源上传

类型：允许用户接入特定的API或者行业垂直媒体，

## 概述

### 问题陈述

- Rimbo 的原生信源体系无法覆盖用户专属情报资产（私有数据库、专有数据流、个人付费订阅）
- 用户目前需要并行运行多套工作流：Rimbo 用于整理信号，其他工具用于监控个人信源
-  缺少自定义信源接入，Rimbo 无法替代现有工作流——只能成为补充工具，而非核心工具

### 战略价值

自定义信源接入是 Rimbo 长期护城河的入口：个人情报资产层。一旦用户的私有信源嵌入其 Brief 生成管道，迁移成本将在结构上变得极高——用户的情报产出质量依赖于 Rimbo 处理其专有输入。

本功能直接回应了用户调研中发现的三个核心需求：

- 「我很常用 Notion——我希望把我的关注列表接进来，让 Rimbo 自动监控这些公司」
- 「GitHub 总是需要我手动重新执行——我希望它自动更新」
- 「我付费订阅了 The Information 和 Stratechery——我希望这些订阅的价值真正体现在我的 Brief 里」

## **目标与成功指标**

### 产品目标

| 编号 | 目标 | 定义 |
|-|-|-|
| G1 | 替代现有工作流 | 用户停止使用独立工具监控信源——Rimbo   成为唯一的情报信息层 |
| G2 | 信源保真度 | 用户自定义信源以与 Rimbo 原生信源相同的质量标准进行处理 |
| G3 | 归因透明度 | 来自用户信源的每条信号均标注信源层级、来源和可信度标记 |
| G4 | 构建护城河 | 用户信源配置形成锁定效应——其 Brief 质量依赖于其信源设置 |

## 功能范围

### API 与数据流接入

接入类型

| **类型** | **信源层级** | **认证方式** | **用户可配置示例** |
|-|-|-|-|
| RSS / Atom 订阅 |  聚合 | 仅需 URL | 付费 Newsletter   RSS（Stratechery、The   Information）、公司 IR RSS、播客订阅 |
| REST API | 一手 | API Key（用户自填） | Bloomberg Terminal API、PitchBook API、自定义内部数据   API |
| Webhook | 一手 | 密钥令牌 | Notion 数据库更新、内部 CRM、专有预警系统 |
| OAuth 集成 | 一手/聚合 | OAuth 2.0 | Google Drive（研究文档）、Notion 工作区、Dropbox |
| 邮件接入 | 聚合 | 转发地址 | 通过邮件投递的付费   Newsletter（Morning Brew、TLDR、行业简报） |

API Key 配置流程

- 用户进入 信源管理页面 → 信源 → 添加自定义信源 → API
- 用户选择接入类型（REST / RSS / Webhook / OAuth / 邮件）
- 用户填写：信源名称、接入 URL 或端点、API Key 或凭证
- 系统执行连接测试并返回：成功确认或具体错误信息
- 用户分配信源层级（系统根据接入类型建议，用户可覆盖）
- 系统按配置频率开始轮询（默认：与频道更新频率一致）
- API Key 加密存储；首次输入后不再完整显示

| **API Key 安全标准** |
|-|
| • 所有 API Key 静态加密存储，使用 AES-256 |
| • 首次保存后以脱敏方式展示（仅显示最后4位字符） |
| • Key 不得出现在日志或错误信息中 |
| • 用户可随时在信源设置中轮换或撤销 Key |
| • 认证失败立即通知用户——不允许静默重试 |

## **信源接入与信号处理管道**

所有用户自定义信源经过与 Rimbo 原生信源相同的四阶段管道处理。唯一的差异在于接入入口。

| **阶段** | **名称** | **处理内容** | **输出** |
|-|-|-|-|
| 1 | 接入 | 文件解析或 API 轮询；原始内容提取；语言检测 | 含元数据的原始文本语料库（信源、时间戳、格式、语言） |
| 2 | 验证 | 信源层级确认；可信度标记应用；与频道实体的相关性核查 | 含 source_tier、credibility_score、entity_links 的验证内容 |
| 3 | 提取 | 事实提取（三元结构：主体+动作+客体）；按信号类型分类识别信号；跨信源去重 | 结构化事实集 + 含归因元数据的信号候选 |
| 4 | Brief 集成 | 按重要性对提取信号排序；集成到   Brief 生成中并附完整信源归因；归因链端到端保留 | 含 source_url、source_tier、attribution_chain 的 Brief 就绪信号对象 |

**Brief 输出中的信源归因**

| **字段** | **值类型** | **示例** |
|-|-|-|
| source_name | 用户自定义标签 | 「NVIDIA Q1 2026   Earnings Call」 |
| source_tier | 一手/聚合/社区 | 「一手信源 」 |
| source_type | 格式类别 | 「PDF 上传 / RSS 订阅 / API」 |
| attribution_chain | 可追溯路径 | 「用户上传 → PDF 提取 → 事实 #3 → 信号」 |

## **用户体验要求**

### 频道设置 — 信源面板

位置：频道设置 → 信源标签页

- 展示：所有活跃信源在统一列表中显示，不区分类型（Rimbo 原生 + 用户自定义）
- 每行信源显示：名称、类型徽标（PDF / API / RSS 等）、层级徽标（一手/聚合/ 社区）、状态（活跃 / 处理中 / 失败）、最后更新时间戳
- 「添加信源」按钮打开信源添加流程（见第4节）

### Chatbox 集成

用户可在不离开聊天界面的情况下在对话中随时添加信源：

- 粘贴 URL → 系统检测是否为订阅源、API 端点或 YouTube 链接并进行路由
- 输入信源指令 → 系统识别意图并打开信源添加流程

### **Brief 归因展示**

- 来自用户信源的每条信号在 Brief 中内联显示信源徽标
- 徽标显示：信源名称 + 层级图标
- 点击徽标展开归因链：来自哪个文档、哪个段落、哪个提取步骤
- 用户可点击「查看原文」查看生成该信号的原始段落

## 边界情况与失败情况

| **场景** | **风险** | **处理要求** |
|-|-|-|
| API Key 在运行中过期或被撤销 | Brief 中出现静默数据缺口 | 立即通知用户；Brief 明确标注「[信源名称] 不可用——最后更新 [日期]」 |
| 用户连接的信源未返回相关内容 | 信号集为空，用户困惑 | 首次轮询后通知：「未发现与您频道关注点匹配的信号，是否检查信源设置？」 |
| RSS 订阅源变更 URL 或失效 | 静默停止更新 | 检测连接异常后立即通知用户，提供重新配置入口 |
| 用户信源与 Rimbo 原生信源内容重复 | 信号重复计算 | 提取阶段去重；同一事实同时出现时，归因于更高层级的信源 |
| Webhook 推送频率过高 | 处理队列拥堵 | 设置推送频率上限；超出限制时排队而非丢弃，通知用户 |

## **依赖项与技术要求**

| **依赖项** | **要求** | **备注** |
|-|-|-|
| API 凭证存储 | 静态 AES-256 加密 | Key 不得出现在日志中；需要轮换 UI |
| RSS 轮询基础设施 | 可配置轮询间隔（最短15分钟） | 遵守订阅源缓存头；失败时指数退避 |
| Webhook 接收服务 | 支持 HTTPS 接收 + 密钥验签 | 推送频率限制；队列持久化 |
| 去重引擎 | 跨信源事实匹配 | 必须在用户自定义信源和   Rimbo 原生信源的统一索引中运行 |
| 归因链存储 | 每条信号的溯源元数据 | Brief 展示需要 source_id → extraction_step → signal_id 链路 |

# Chat 中的“频道创建”链路逻辑



**步骤1：用户输入需求**

**用户操作**：用户在 Chatbox 中输入内容

- **触发条件**：用户输入中包含以下任意意图，均触发频道创建链路：

1. 明确追踪意图：包含"追踪/关注/订阅/monitor/track/follow"等关键词
2. 实体+动态意图：包含具体实体名称（公司/人物/话题）+ "动态/新闻/更新/news/update"等关键词
3. 无关键词但语义明确：如"我想知道NVIDIA最近在做什么" / "帮我盯着Elon Musk"



**步骤2：识别关键词和内容提取**

- **系统行为**：系统需要对用户输入进行自然语言处理（NLP），提取关键词：

实体名称    用户想追踪的是谁/什么 例：NVIDIA、Elon Musk、AI行业、加密市场

实体类型    自动判断属于哪个类型  Person / Company / Industry / Topic
