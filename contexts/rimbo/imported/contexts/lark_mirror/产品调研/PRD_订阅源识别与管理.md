# PRD_订阅源识别与管理

### **1. 概述**

#### **1.1. 产品背景**

需求：**系统化地识别用户深度信任的信息源（信源忠诚度），并将其构建为一个可供用户可视化管理的“个人订阅源”系统。**

#### **1.2. 核心目标**

- **自动化发现**：通过分析跨平台行为数据，自动识别用户拥有高忠诚度的信源。
- **归一化处理**：**将用户在不同平台接触到的信息源统一关联到其背后的实际发布者，提升了构建用户跨渠道兴趣画像的效率和准确性。**
- **用户协同管理**：为用户提供订阅源列表与管理功能，实现系统自动推荐与用户手动管理的闭环。
- **提升信息流质量**：将已验证的高忠诚度信源作为最高优先级的内容抓取源头，显著提升推送内容的相关性与价值感知。

**步骤二：信源归一化与画像建构（核心服务）**

- **输入**：从各平台抓取的、非结构化的信源字符串。
- **处理**：

  1. **唯一标识**：为不同平台来源的信源生成唯一的 `source_id`。
  2. **内容类型分类**：为信源打上主导内容类型标签，如 `newsletter`, `podcast`, `blog`, `social_media_account`。一个信源只对应一个类型。
  3. **领域归类**：使用分类模型或关键词匹配，为信源打上领域标签（如 `Technology -> AI`）。
  4. **关联到统一的发布者：提取发布者名称，生成publisher_id，将同一发布者的不同信源关联起来，例如："a16z_newsletter_gmail"和"@a16z"都关联到publisher_id: "a16z"**
- **输出**：标准化的信源对象，作为系统的基础数据。

#### **2.2. 信源忠诚度计算与“个人信源图谱”构建**

- **输入**：用户的跨平台行为数据 + 标准化信源对象。
- **忠诚度信号量化**量化：为一个用户-信源对，计算信源忠诚度分数（0-1），不需要交叉验证，取三个平台中强度最高的数值即可。

  | 平台 | 忠诚度信号 | 量化逻辑 |
  |-|-|-|
  | Gmail | 关系强度 | 订阅时长 > 3个月，平均打开率 > 60% |
  |  | 互动投入 | 链接点击率，回复/转发行为，重复打开 |
  |  | 内容处置 | 为其创建专属文件夹/标签 |
  | Twitter | 关系强度 | 关注时长 > 60天，加入专属列表 |
  |  | 互动投入 | 高频浏览其主页，书签行为，深度阅读 |
  | Notion | 关系强度 | 页面创建时间长，定期访问 |
  |  | 互动投入 | 大量引用其内容，为其建立结构化笔记 |



- **输出与存储**：为每个用户构建并维护一个 信源列表：**`user_managed_status`** 状态机：

  ```JSON
  {
    "user_id": "user_123",
    "source_id": "benedict_evans_newsletter",
    "strength": 0.88,
    "user_managed_status": "auto_subscribed", // 核心管理字段
    "discovery_date": "2024-05-20",
    "last_activity_signal": "2024-06-15"
  }
  ```

  - `auto_subscribed`：系统自动识别并加入（当 `strength` > 阈值，即不是所有的信源都要被系统自动订阅。）。理由：不应将用户历史上关注的所有信源都自动纳入。用户关注列表（Followed List）中存在大量 **inactive（不活跃）或过期**的信源，这些信源已不再反映用户**当前**的真实兴趣，盲目纳入会导致兴趣画像失准。
  - `user_subscribed`：用户手动订阅某个 `auto_subscribed` 的信源。
  - `user_unsubscribed`：用户手动退订。**此状态的信源不应再出现于信息流，且其行为数据应作为负反馈。**

#### **2.3. 用户订阅源管理**



- **功能**：在UI界面“我的订阅源”中，允许用户集中管理其信源图谱。
- **用户操作**：

  1. **查看**：可按类型（如 `newsletter`, `podcast`, `blog`, `social_media_account` ） 浏览所有 `auto_subscribed` 和 `user_subscribed` 的信源。
  2. **订阅：**主动搜索订阅新信源。
  3. **退订**：将任何信源设置为 `user_unsubscribed`。
  4. **调整优先级**：对特定信源标记“特别关注”（更新提醒）
- **业务逻辑**：用户的所有操作都通过API更新 `user_managed_status` 字段。此字段是后续内容推送的最高优先级规则。

#### **2.4. 信息流生成逻辑的变更**



现有的意图推理引擎需集成信源忠诚度信号。此外，内容获取器（Fetcher）的优先级逻辑应修改为：



1. **第一优先级**：抓取所有 `user_subscribed` 信源的最新内容。
2. **第二优先级**：抓取 `auto_subscribed` 信源的最新内容。
3. **第三优先级**：基于其他意图（如项目执行、兴趣探索）进行全网内容发现。

**信息流卡片类型**：

- **`核心信源聚合流`**：为有多个高强度的 `user_subscribed`  信源归一的`publisher_id`创建专属信息流，聚合其跨平台（博客、Newsletter、Twitter等）的所有内容更新。
