## 1. 文档结论

本文提出一套面向小红卡活动的配置化 V2 方案，目标是在 RN 已内置组件能够覆盖需求的前提下，新增活动只需要创建配置和发布版本，不再按照活动 ID 修改前端页面代码。

核心结论：

- 老活动继续使用原路由、原接口和原 Apollo 配置，不迁入 V2 即不受影响。

- 新活动使用新的详情路由、新详情接口、新写接口和版本化配置库。

- Config 只保存活动固定规则、固定内容和页面模板，不保存用户报名、中奖、库存、积分和票务等动态数据。

- 服务端负责读取 Config、查询实时业务数据、计算唯一 sceneCode，并编译出最终页面文档。

- RN 只按照页面协议渲染模块和执行白名单动作，不根据时间、中奖状态或活动 ID推导页面。

- 页面协议采用受约束的 Server-Driven UI 形式：允许组合已注册模块，不允许配置任意 RN 样式、动态 JavaScript 或通用表达式。

- 抽奖、积分兑换、免费兑换使用同一套页面协议，但分别进入独立业务 Handler。

<redoc-highlight emoji="tuding" fillColor="yellow">
配置决定“这个活动固定是什么”；实时接口决定“当前用户此刻是什么状态”；详情编译器决定“当前页面最终展示什么”；RN 只负责渲染和触发动作。
</redoc-highlight>

## 2. 当前实现及问题

当前实现分散在三端：

- RN：packages/red-card-member-activity/src/main.tsx 固定编排 KV、信息区、结果区、阵容、活动亮点、相关笔记、规则和底部按钮。

- RN：src/theme/activityTheme.ts 和 src/config/activityConfig.ts 按 activityId 保存主题、直接报名和票务链接等差异。

- IDL：ActivityDetail 是固定字段集合，新增页面能力通常需要增加 IDL 字段。

- 后端：ActivityConfig 同时承载活动业务字段和展示字段。

- 后端：ActivityApolloConfig 从 redvip.activity.config.list 一次性读取全部活动配置。

- 后端：ActivityQueryService 负责计算活动阶段、用户报名、中奖、积分和票务状态，但尚未输出统一页面场景和最终 Page Document。

现有模式适合少量同构活动，但随着抽奖、积分兑换、免费兑换、不同结果卡、不同按钮数量和不同跳转方式增加，会出现以下问题：

- RN 持续增加 activityId 分支。

- 页面状态由前端重复推导，容易和服务端业务状态不一致。

- 页面固定内容、业务规则和用户动态数据边界不清晰。

- Apollo 单列表缺少草稿、版本、校验、预览、发布和审计能力。

- 单一底部按钮模型无法覆盖模块内按钮、双按钮和不同动作。

- ticketCount 同时表达库存、中奖数或票数时语义不稳定。

## 3. 目标与非目标

### 3.1 目标

- 新活动在组件能力已覆盖时，实现零 RN 代码新增。

- 同一协议覆盖抽奖、积分兑换和免费兑换详情页。

- 支持不同场景下模块增删、顺序变化、结果卡差异和一到多个按钮。

- 支持固定内容、动态业务数据和最终展示数据的明确分层。

- 支持配置草稿、校验、预览、发布、回滚和审计。

- 页面预览和线上详情使用同一个服务端编译器。

- 写操作由服务端再次校验，不能信任客户端携带的 Scene 或按钮状态。

### 3.2 非目标

- V2 不兼容或复用老 ActivityDetail 字段。

- V2 不支持服务端下发任意 RN StyleSheet。

- V2 不支持配置动态 JavaScript、通用条件表达式或任意接口请求。

- V2 不保证完全不发 RN 版本；新增组件类型或新的交互能力仍需要发版。

- 本期不把 Apollo 改造成正式活动管理后台；Apollo 只适合作为过渡配置源。

## 4. 总体架构

<redoc-text-draw remoteTemplate="flowchart LR
Admin[活动后台或配置库] --> Config[已发布活动 Config]
Config --> Compiler[页面编译器]
Runtime[报名 中奖 库存 积分 票务] --> Compiler
Compiler --> Detail[queryActivityPageV2]
Detail --> Renderer[RN PageRenderer]
Renderer --> Registry[组件注册表]
Renderer --> Action[ActionDispatcher]
Action --> Command[executeActivityActionV2]
Command --> Handler[Lottery Points Free Handler]" theme="light"/>

整体数据流：

1. 活动运营在后台创建草稿 Config。

2. 发布服务使用 JSON Schema 校验 Config 和所有组件 Props。

3. 发布后生成不可变的 configVersion。

4. 用户查询详情时，服务端读取已发布 Config。

5. 服务端查询报名、中奖、填写、库存、积分和票务等运行态。

6. Scene Resolver 计算唯一 sceneCode。

7. Page Compiler 合并模块基础 Props、Scene Override 和实时数据。

8. 详情接口返回当前用户最终可渲染的 Page Document。

9. RN Renderer 按 type + version 找到本地组件并渲染。

10. 用户点击服务端命令按钮时，统一写接口重新读取配置和实时状态并再次校验。

## 5. 数据边界

| 数据类型 | 示例 | 真源 | 是否进入 Config | 是否由详情接口返回 |
| --- | --- | --- | --- | --- |
| 固定业务规则 | 报名时间、开奖时间、奖品数量、填写截止时间 | 已发布 Config | 是 | 页面或运行态需要时返回 |
| 固定展示内容 | KV、阵容、亮点、笔记、规则、中奖奖品展示文案 | 已发布 Config | 是 | 编译到模块 Props |
| 页面结构 | 模块顺序、组件版本、按钮布局、Scene 模板 | 已发布 Config | 是 | 编译成最终 Page Document |
| 用户状态 | 是否报名、是否中奖、填写状态 | 业务数据库 | 否 | 是 |
| 资源状态 | 剩余库存、用户积分、门票状态 | 库存、积分、票务系统 | 否 | 按活动类型返回 |
| 最终 Scene | LOTTERY_WON_NEED_ENTRY | 服务端计算 | 否 | 是 |
| 最终按钮可用性 | 是否可点、禁用原因 | 服务端计算 | 否 | 是 |

### 6.1 明确不进入 Config 的字段

以下信息必须来自实时业务数据：

- 当前用户是否报名。

- 当前用户是否中奖。

- 当前用户填写了几位观演人。

- 当前观演人姓名、证件类型和脱敏证件号。

- 当前积分余额。

- 当前剩余库存。

- 当前门票是否生成、使用、转赠或过期。

- 当前按钮是否可点击及禁用原因。

- 当前 sceneCode。

### 6.2 配置引用规则

允许的引用只有两类：

- Scene 通过 moduleIds 和 footerActionGroup 引用同一 Page 内已定义的模块及按钮组。

- ticketTemplateId、inventoryPoolId 等引用外部业务系统中的稳定实体 ID。

不允许：

- contentRef: content.lineup 一类任意 JSON 路径。

- configRef: business.xxx 一类跨层路径。

- &#123;&#123;runtime.user.isWinner&#125;&#125; 一类运行时表达式。

- 服务端下发任意 RN StyleSheet 或组件类名。

## 7. 页面协议

### 7.1 Page Document

详情接口最终返回的 page 遵循以下逻辑结构：

```typescript
interface ActivityPageDocument {
  activityId: string
  activityType: 'LOTTERY' | 'POINTS_EXCHANGE' | 'FREE_EXCHANGE'
  protocolVersion: string
  configVersion: number
  sceneCode: string
  serverTime: number
  refreshAfterMs?: number
  page: {
    theme: ActivityTheme
    modules: PageModule[]
    footer?: ActionGroup
  }
  runtime: ActivityRuntime
}

interface PageModule {
  id: string
  type: string
  version: number
  slot: 'HERO' | 'RESULT' | 'CONTENT' | 'FLOATING'
  props: Record<string, unknown>
}
```

Record&lt;string, unknown&gt; 只是传输层表现。每个 type + version 都必须有独立 JSON Schema 和 TypeScript Props 类型，例如 RESULT_CARD@1、LINEUP@1，不能将它当成任意 JSON。

### 7.2 首期组件注册表

| 组件 | 版本 | 职责 |
| --- | --- | --- |
| HERO | 1 | 顶部 KV、沉浸式导航适配 |
| BASIC_INFO | 1 | 活动标题、时间、地点、票种和描述 |
| RESULT_CARD | 1 | 报名、开奖、中奖、填写和票务结果 |
| LINEUP | 1 | 普通阵容或时间轴阵容 |
| HIGHLIGHT_CAROUSEL | 1 | 活动亮点横滑模块 |
| NOTE_CAROUSEL | 1 | 相关笔记横滑模块 |
| RULE_LIST | 1 | 结构化活动规则和协议链接 |
| ACTION_GROUP | 1 | 单按钮、双按钮和纵向按钮布局 |

组件协议采用显式版本。例如新增完全不同的结果卡结构时注册 RESULT_CARD@2，而不是向 RESULT_CARD@1 无限添加可选字段。

### 7.3 Action 协议

首期动作白名单：

| 动作 | 是否写请求 | 说明 |
| --- | --- | --- |
| SERVER_COMMAND | 是 | 报名、积分兑换、免费领取、提交信息、转赠等 |
| OPEN_SCREEN | 否 | 打开已注册的 RN 子页面 |
| OPEN_LINK | 否 | 打开经过服务端校验的 Deeplink 或 HTTPS 链接 |
| COPY_TEXT | 否 | 复制固定文本并 Toast |
| OPEN_MODAL | 否 | 打开已注册标准弹层 |
| CLOSE_PAGE | 否 | 关闭当前页面 |

配置只能选择动作类型及其标准参数，不能配置任意 Bridge 方法。

## 8. 详情接口方案

### 8.1 接口定义

新增 V2 接口，不修改老接口语义：

```plaintext
queryActivityPageV2(activityId)
```

请求：

```json
{
  "activityId": "night_festival_2026"
}
```

响应示例：

```plaintext
{
  "response": {
    "success": true,
    "code": 0,
    "msg": "success"
  },
  "activityId": "night_festival_2026",
  "activityType": "LOTTERY",
  "protocolVersion": "1.0",
  "configVersion": 12,
  "sceneCode": "LOTTERY_WON_NEED_ENTRY",
  "serverTime": 1786352400000,
  "refreshAfterMs": 30000,
  "pageDocumentJson": "{...}",
  "runtimeJson": "{...}"
}
```

第一期 IDL 推荐使用强类型信封加已校验 JSON 文档：

```plaintext
struct QueryActivityPageV2Response {
    1: required Response response,
    2: optional string activityId,
    3: optional string activityType,
    4: optional string protocolVersion,
    5: optional i64 configVersion,
    6: optional string sceneCode,
    7: optional i64 serverTime,
    8: optional i64 refreshAfterMs,
    9: optional string pageDocumentJson,
    10: optional string runtimeJson,
}
```

选择该形式的原因：

- 页面组件 Props 是多态结构，直接在 Thrift 中为每个组件建立大型 Union 会导致每次新增组件都发布 IDL。

- JSON 并不等于无协议；发布配置、服务端编译结果和 RN 接收端都必须按同一份 JSON Schema 校验。

- activityId、版本、Scene 和服务端时间仍保留为强类型一级字段，便于网关、监控和缓存使用。

协议稳定后，可以将高频公共字段提升为强类型 Thrift，但不应同时维护两套不同语义的 Page Document。

### 8.2 字段解释

| 字段 | 来源 | 含义 |
| --- | --- | --- |
| response | 服务端 | 通用成功状态和错误码 |
| activityId | Config | 活动唯一 ID |
| activityType | Config | 业务 Handler 类型 |
| protocolVersion | 页面协议 | Page Document 的协议版本 |
| configVersion | 配置发布记录 | 当前使用的不可变发布版本 |
| sceneCode | Scene Resolver | 当前用户唯一权威场景 |
| serverTime | 服务端 | 当前毫秒时间，避免使用设备时间推导状态 |
| refreshAfterMs | 服务端计算 | 建议客户端下次刷新间隔；为空表示不需要自动刷新 |
| pageDocumentJson | Page Compiler | 已完成合并、可以直接渲染的页面文档 |
| runtimeJson | 业务查询 | 当前用户运行态，供表单、刷新、埋点和调试使用 |

## 9. Scene 计算

### 9.1 抽奖型 Scene

## 10. 前端方案

### 10.1 路由和包结构

建议新增独立 V2 页面包和路由：

```plaintext
packages/red-card-activity-v2/
  src/
    apis/
    components/
    protocol/
    renderer/
    actions/
    screens/
    store/
    tracker/
    main.tsx

route: /red-card-activity-v2
```

老 red-card-member-activity 和 red-card-member-points-activity 保持原接口和行为。活动迁移时由入口配置整体切换到新路由，不在 V2 Renderer 中增加老字段 fallback。

### 10.2 协议层

protocol/ 包含：

- Page Document TypeScript 类型。

- 各组件 Props 类型。

- 各 Action 参数类型。

- JSON Schema 运行时校验器。

- protocolVersion 和组件版本支持矩阵。

接口返回后先完成以下校验：

1. protocolVersion 是否受支持。

2. 每个 type + version 是否在组件注册表中。

3. 每个模块 Props 是否通过对应 Schema。

4. Action 类型和参数是否在白名单中。

失败时上报协议错误并进入统一错误页，不能静默渲染未知结构。

### 10.3 组件注册表

```typescript
const componentRegistry = {
  'HERO@1': HeroV1,
  'BASIC_INFO@1': BasicInfoV1,
  'RESULT_CARD@1': ResultCardV1,
  'LINEUP@1': LineupV1,
  'HIGHLIGHT_CAROUSEL@1': HighlightCarouselV1,
  'NOTE_CAROUSEL@1': NoteCarouselV1,
  'RULE_LIST@1': RuleListV1,
} as const
```

Renderer 只负责：

- 按接口数组顺序渲染模块。

- 根据 Slot 处理沉浸式 KV、内容区和悬浮层。

- 渲染 Footer ActionGroup。

- 处理安全区、Android 透明状态栏和最大 420px 内容窗口。

- 对模块曝光和按钮点击统一埋点。

Renderer 不负责：

- 根据时间判断活动阶段。

- 根据用户状态判断是否中奖。

- 根据活动 ID 选择主题和按钮行为。

- 拼接奖品名称、门票数量和中奖文案。

- 判断库存、积分或写操作是否允许。

### 10.4 样式边界

配置可控制：

- 主题语义色。

- 组件 Variant。

- 模块是否展示和顺序。

- 按钮布局和语义样式。

RN 组件固定：

- 281px 按钮宽度等设计尺寸。

- 字号、字重、圆角、间距。

- Android 加 100 字重等平台差异。

- 折叠屏和最大内容宽度。

- SVG 字形和主题色条的叠放规则。

### 10.5 ActionDispatcher

ActionDispatcher 统一处理：

- OPEN_SCREEN：校验 Screen 注册表并打开子页面。

- OPEN_LINK：校验 Scheme 或 HTTPS 白名单后跳转。

- COPY_TEXT：写剪贴板并展示接口下发的 Toast。

- SERVER_COMMAND：生成幂等键并调用统一写接口。

服务端命令成功后，RN 必须重新请求 queryActivityPageV2，不能只在本地猜测下一个 Scene。

### 10.6 缓存和 Preload

缓存键至少包含：

```plaintext
activityId + userId + configVersion + protocolVersion
```

推荐策略：

- 首屏可以先展示上次成功缓存。

- Preload/Fresh 返回后只用权威结果替换一次页面。

- 缓存中同时保存完整 Page Document 和 Runtime，不能只缓存模块列表。

- refreshAfterMs 到期或跨越报名、开奖、截止时间时必须刷新。

- 写操作成功后主动失效当前活动用户缓存。

- Preview 响应使用独立缓存命名空间，绝不能污染线上缓存。

## 11. 后端方案

### 11.1 新增领域边界

建议新增以下核心能力：

```plaintext
ActivityConfigRepository
ActivityConfigValidator
ActivityRuntimeQueryService
ActivitySceneResolver
ActivityPageCompiler
ActivityActionService
ActivityTypeHandler
```

职责：

- ActivityConfigRepository：按活动和发布版本读取不可变 Config。

- ActivityConfigValidator：校验顶层 Config、模块 Props、Scene 引用和 Action 白名单。

- ActivityRuntimeQueryService：查询当前用户和资源运行态。

- ActivitySceneResolver：根据 Config 和 Runtime 计算唯一 Scene。

- ActivityPageCompiler：生成最终 Page Document。

- ActivityActionService：统一校验、幂等和命令分发。

- ActivityTypeHandler：实现不同活动类型的查询及写操作差异。

### 11.2 Handler

```java
public interface ActivityTypeHandler {
    String activityType();

    ActivityRuntime queryRuntime(
        String activityId,
        String userId,
        PublishedActivityConfig config
    );

    String resolveScene(
        PublishedActivityConfig config,
        ActivityRuntime runtime,
        Instant now
    );

    ActionResult execute(
        ActivityActionCommand command,
        PublishedActivityConfig config
    );

```

首期实现：

- LotteryActivityHandler

- PointsExchangeActivityHandler

- FreeExchangeActivityHandler

不要让 ActivityQueryService 继续通过大量 if activityType 承载所有活动类型。

### 11.3 页面编译顺序

Page Compiler 按固定顺序执行：

1. 读取当前 Scene 配置。

2. 根据 moduleIds 选择模块并保持顺序。

3. 复制模块基础 Props。

4. 合并当前 Scene 的 moduleOverrides。

5. 由对应 Module Enricher 填入动态 Props。

6. 解析当前 Scene 的 Footer ActionGroup。

7. 根据实时权限计算 enabled 和 disabledReason。

8. 输出最终 Page Document 并按协议 Schema 再校验一次。

例如 ResultCardEnricher 负责写入：

- 实际中奖状态。

- 有效填写截止时间。

- 脱敏观演人列表。

- 当前门票状态。

它不能修改 Config 中的固定 rewardText。

### 11.5 强库存

积分兑换和免费兑换不能继续使用“查询已兑换数后再判断”的弱一致方式。建议独立库存表：

```sql
activity_session_inventory
- activity_id
- config_version
- session_id
- total_count
- issued_count
- reserved_count
- version
```

领取时使用数据库原子条件更新或统一库存服务：

```sql
update activity_session_inventory
set issued_count = issued_count + 1,
    version = version + 1
where activity_id = ?
  and session_id = ?
  and issued_count + reserved_count < total_count
  and version = ?;
```

语义必须拆分：

- 抽奖：winnerCount。

- 积分/免费兑换：inventoryPoolId 或库存表总量。

- 每人获得票数：reward.quantity。

- 每张票对应观演人数：填写或票务模板规则。

不再让 ticketCount 同时表达多个概念。

## 12. 统一写接口

新增：

```plaintext
executeActivityActionV2
```

请求：

```plaintext
{
  "activityId": "night_festival_2026",
  "actionId": "joinLottery",
  "sceneCode": "LOTTERY_JOINABLE",
  "configVersion": 12,
  "idempotencyKey": "client-generated-uuid",
  "inputJson": "{}"
}
```

服务端处理顺序：

1. 重新读取当前发布配置。

2. 校验客户端 configVersion 是否仍有效。

3. 重新查询 Runtime。

4. 重新计算 Scene。

5. 校验 actionId 是否属于当前 Scene 且可执行。

6. 校验输入 Schema。

7. 进入对应活动 Handler。

8. 使用 idempotencyKey 保证写操作幂等。

9. 返回操作结果和最新详情，或让 RN 立即回刷详情。

客户端传入的 sceneCode 只用于并发冲突检测，不能作为服务端授权依据。

命令集合：

- LOTTERY_JOIN

- POINTS_EXCHANGE

- FREE_CLAIM

- SUBMIT_ENTRY_INFO

- TRANSFER_TICKET

- REDEEM_CODE

## 13. 配置校验和发布

发布前必须完成：

- 顶层 Config JSON Schema 校验。

- 活动类型专属 Business Schema 校验。

- 每个 type + version 的 Props Schema 校验。

- Module ID 和 ActionGroup ID 唯一性校验。

- Scene 引用完整性校验。

- URL Scheme 和 HTTPS 域名白名单校验。

- joinStartAt、joinEndAt、drawAt、activityStartAt、activityEndAt 顺序校验。

- reward.quantity、entry.personCount 和票务模板规则一致性校验。

- 所有 Scene 至少能编译成一个合法 Page Document。

- 当前线上最低 RN 版本是否支持配置中使用的全部组件版本。

发布生成新版本，不覆盖旧版本。线上查询只读取 PUBLISHED 版本；回滚只需要将当前发布指针切回之前版本。

## 14. 预览方案

预览不能把动态 Mock 写进正式 Config。

流程：

1. 用户选择一个草稿版本。

2. 后台选择 Mock Scene，例如 LOTTERY_WON_NEED_ENTRY。

3. 后台生成短期有效的 Preview Token。

4. 预览接口读取草稿 Config 和独立 Mock Runtime。

5. 使用与线上相同的 Page Compiler 生成页面。

6. RN 预览页展示水印，并禁用所有写操作。

Preview Token 至少绑定：

- activityId。

- configVersion。

- mockSceneCode。

- operator。

- expiresAt。

## 16. 兼容与迁移

| 维度 | V1 | V2 |
| --- | --- | --- |

## 20. 风险和控制

| 风险 | 控制方式 |
| --- | --- |
| 配置能力无限膨胀 | 只允许白名单组件、Variant 和 Action |
| Page JSON 失去强类型 | JSON Schema、生成 TypeScript 类型、服务端和 RN 双重校验 |
| 服务端与 RN 组件版本不一致 | 发布时检查线上最低 RN 支持矩阵 |
| 页面状态与业务状态不一致 | Scene 只由服务端计算，写请求再次校验 |
| 缓存展示旧页面 | 缓存键包含用户、Config 和协议版本，并支持临界时间刷新 |
| 免费兑换超卖 | 原子库存扣减和幂等记录 |
| 预览误触真实写操作 | Preview 独立 Token、缓存和 Mock Runtime，写操作强制禁用 |
| 固定展示文案与履约参数冲突 | 发布校验 rewardText、reward.quantity 和票务模板 |

## 21. 待确认项

- V2 正式配置库是直接建设活动后台数据库，还是先使用 Apollo 单活动 Key 过渡。

- winnerCount 是否由现有开奖任务直接读取；若开奖流程外部传入人数，则从 Config 删除。

- 票务模板是否可以校验每份奖品数量和观演人数。

- 第一批必须支持的 RESULT_CARD Variant 清单。

- 后台是否已有可复用的 Page Schema Framework；若使用公司既有 PSF，需要对齐其 RN Renderer、Schema 管理和发布能力。

- 页面协议 JSON Schema 的代码生成工具及真源仓库。
