# 工程交付与验证

适用场景：修 bug、环境修复、发布、回滚、MCP、Chrome、数据库、部署、mock、hard-cut、git/worktree。

## 诊断与验证

- 先恢复系统基线，再做下游验收；底层服务、路由、DNS、关键进程和过滤器不稳时，UI symptom 没诊断价值。
- 本机卡顿或性能异常先做只读体检并连续采样，优先区分单进程 CPU 打满、内存压缩与 `swap`、磁盘空间和温控，再决定是否继续追某个表面 symptom。
- 用户改了一个变量，就以这个变量为起点重做 baseline 和 A/B。
- 不把 `--help`、README、插件已安装、extension enabled 当成可用性证明；要补真实 smoke。
- 静态验证、运行时链路、用户可见验收要分层报告，不能混成一句“已验证”。
- 本机 symptom 消失时，继续区分“上游已修复”还是“本地 workaround 在遮蔽”。
- 只读 SQL、源码、POM、已登录浏览器或文件时间戳足够回答问题时，优先走最短真源路径。

## Git、worktree 与发布

- 默认保护脏工作区，不 reset、不覆盖、不替用户清场。
- worktree 是显式隔离工具，不是默认逃生舱；只有用户明确要隔离修复，或主工作树风险过高时才用。
- 用户指定了分支、worktree 或“就按当前本地状态发布”时，改动前重查 `git branch --show-current`、`git status -sb`、`git worktree list` 和相关锁；旧 summary 里的 branch 名只能当历史证据。
- “push 一个分支”的完成态是远端结果可见；没有 tracked diff 时不要制造空提交。
- 跨分支 merge/cherry-pick 时，业务改动和目标分支环境合同分开处理，保住目标分支自己的运行时基线。
- 发布前检查要把真实阻塞、既有噪声、环境不兼容和流程硬门禁拆开，不把所有红字都当 blocker。
- 分支 `SNAPSHOT` 编译通过，不代表正式制品已等价；正式发布后要回读官方产物或做下游最小编译。

## 合同、完成态与 provenance

- 任务合同只能有一个真源；已有 `Profile`、schema、quality gate 时，不再保留兜底任务定义。
- 计数、复杂度、coverage、门禁都要绑定原子单元，不用文件数或弱 source 数量做代理。
- `complete_with_gaps`、`answered_with_gap` 等完成态依赖 Backend 持久化 Need 终态，不让模型自己猜。
- provenance 敏感字段只信持久化 checkpoint、canonical receipt 和已验证快照；不信模型自报 URL、quote 或 `sourceType`。
- fallback 只能兜底，不能抢主路径；已有完整主文档时，不用简化骨架覆盖交付。

## 环境、工具链与内部系统

- 旧项目环境冲突时，以 `.nvmrc`、lockfile、真实 CLI 版本和成功 bundle/请求为准，再回写 README。
- 陌生仓库先看包装层和包管理器副作用，再跑 `pnpm exec`、构建 CLI 或升级脚本。
- MCP / skill 缺席要分层诊断：`documented`、`installed/configured`、`handshake`、`task-visible`。
- 第三方 API、MCP、券商或平台接入要再补一层资格诊断：`eligible/credentialed`。已有用户主账号，不等于已有 Developer Portal、App Key 或可执行写操作的授权链路。
- 私有 CLI / skill 的 401，要一起检查认证、依赖和定位链路；修通后把凭证留在系统密钥库并补只读 smoke。
- 内部文档系统优先走 canonical CLI / skill，浏览器只做补验。

## UI、mock 与 hard-cut

- 临时 mock 只能做验证；验证后立刻删除，不保留误提交开关。
- hard-cut 先核对用户限定的场景和共享能力，再清理该范围内的路由、状态、调度、测试和文档；删除一个场景入口时保留其他场景仍使用的能力。
- 表单从有值改为空时，沿校验、变更检测、请求适配和持久化回读核对清空语义；放宽必填不能代替保存。区分省略字段、`null` 和业务约定的清空值，测试必须验证请求实际发出及参数，不能只验证表单通过。
- 兼容性修复优先回放真实接口响应；文档与运行时的枚举、哨兵值或字段不一致时，以当前环境响应及持久化回读定位差异，再同步参数、测试和说明。明确业务拒绝与超时未知结果分开处理；写请求超时后先查询状态，再决定是否重试。
- 通过主项目和代理验收时，核对规则语法、启用状态、协议匹配及实际资源来源。验收远端发布前关闭本地替换并重新加载，分别证明平台版本、资源可达和远端页面生效。
- 分享场景 URL 或原生深链前，核对页面确实读取参数、目标实体与路由类型一致；覆盖缺省和非法值，并区分代码已支持与目标环境已发布。
- 浏览器端引用、viewer 和定位能力要继承既有交互合同，不为了补功能破坏原阅读路径。

## 埋点与指标核验

- 沿组件触发条件、指令、SDK 组装与发送、平台注册、接收记录和统计查询逐层核对。数字点位 ID 与 `event_key` 分开记录；字典搜索未命中时，继续核对发送代码和可用的原始事件查询入口，分别报告代码存在、请求发出、服务端收到与统计可查。
- 共用点位先核对接口实际返回值和后端字段映射，再确定筛选条件；按钮文字不同不代表事件可区分。计算 CTR 前固定入口、人群、状态、环境、时间窗口和去重标识，分子分母范围一致；周期 UV 整体去重，暂无数据不能填 0，混入旧版本或其他入口时说明指标边界。
- 埋点验收按宿主、来源、角色、环境、交互阶段列明已触发与未触发项。开发或 Beta 探查有记录，只证明对应测试链路；共享组件、部分字段修改或按钮校验通过，不能代替另一宿主、提交结果和生产统计验收。
