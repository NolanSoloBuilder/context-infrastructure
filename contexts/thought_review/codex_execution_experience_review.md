## 一、执行经验总结

### 1. 先读规则，再动手

问题做法：进入 workspace 后直接搜索或改文件，容易忽略目录路由、沟通规则、测试约束和已有 skill。

正确做法：每次先读取 `AGENTS.md` 要求的 `rules/SOUL.md`、`rules/USER.md`、`rules/WORKSPACE.md`、`rules/COMMUNICATION.md`、`rules/skills/INDEX.md`。找文件时先看 `rules/WORKSPACE.md`，再用 `rg` 定位。

教训：这个仓库的价值在于长期上下文。跳过规则会让 agent 退化成一次性脚本执行器。

### 2. 结论必须落到文件

问题做法：把产品判断、架构方案、调研结论只留在聊天里，后续 session 无法继承。

正确做法：凡是后续可能复用的结论，都按 `rules/WORKSPACE.md` 写入对应目录。调研报告进 `contexts/survey_sessions/`，复盘和方法论进 `contexts/thought_review/`，可复用流程进 `rules/skills/`，长期协作规则进 `AGENTS.md` 或 `rules/`。

教训：文件是这个系统的长期记忆接口。聊天里的判断只有被写成文档，才会变成可继承资产。

### 3. 不用印象替代真实链路

问题做法：看到现象后只按经验解释，或者只看 UI / README / 文件存在就下结论。

正确做法：沿真实链路核对代码、配置、数据库、缓存、运行时、部署和日志。涉及 OpenAI / 第三方 / 时间敏感信息时查官方文档或真实状态。涉及浏览器验证时使用 Codex 插件控制本地 Chrome。

教训：徐昊更看重可验证的闭环，而不是看起来合理的解释。

### 4. 保护本地工作区

问题做法：为了让当前任务变干净，直接 reset、checkout 或覆盖已有改动。

正确做法：先 `git status --short`。只改本次任务相关文件；遇到已有改动默认视为用户或其他任务的工作成果。需要跨分支、merge、stash 或清理时，先确认影响范围。

教训：本地脏工作区是常态。工程动作要以“不破坏已有工作”为底线。

### 5. Hard-cut 要做完整

问题做法：用户说产品没上线、不需要兼容、目前不透出时，只做视觉隐藏或入口隐藏。

正确做法：同时清理入口、路由、open-state、dialog、guide、scheduler、tests、docs 和共享依赖边界。删除前必须查 call sites，避免误删仍被其他功能复用的类型或存储。

教训：产品未上线时，长期合理性优先于表面兼容。完整下线比半隐藏更可维护。

### 6. 失败经验要写成规则

问题做法：修完一个环境、CLI、MCP、缓存、日志或部署问题后，只汇报“修好了”。

正确做法：补充“症状、原因、正确处理方式、下次默认动作”。如果是跨项目可复用经验，写到 `rules/skills/` 或本文件。

教训：同类问题一定会再次出现。可复用规则比一次性修复更有价值。

### 7. 先恢复系统基线，再做下游验收

问题做法：浏览器、页面、Chrome bridge 或 UI 展示异常时，立刻在壳层现象上打转。

正确做法：先恢复底层基线，再做下游验证。对 Mindspace 这类三服务链路，先确认 `8099/8079/9090` 都健康；对系统网络问题，先看默认路由、DNS、关键进程和过滤器状态。只有底层健康后，浏览器验收才有解释力。

教训：下游 symptom 噪声很大。底层没站稳时，Chrome、loading shell、UI 空白都不具备诊断价值。

### 8. 用户改了一个变量，就做一次新的单变量诊断

问题做法：用户已经关闭后台隧道、重启机器或换了一个运行状态后，仍沿用旧结论，或者继续叠加新的猜测性操作。

正确做法：把用户刚刚改动的那个变量当成新的起点，立即重采 baseline，再围绕这一个变量做 A/B。必要时明确写出“启用时怎样、停用时怎样、重启后怎样”。

教训：能归因的诊断，比“看起来修好了”的描述更有复用价值。

### 9. 历史方案与当前状态必须分开验证

问题做法：把“之前调研过”“之前做过”“之前安装过”直接当成当前事实。

正确做法：凡是涉及账号状态、平台条款、provider endpoint、浏览器扩展、native host、MCP 连接、自动化集成的事，都要把历史方案和当前实况拆开验证。历史记录只能提供搜索入口，不能替代 live check。

教训：这类系统最容易漂移。旧方案、旧路径、旧授权状态和现在往往不是同一回事。

### 10. 输出偏好与能力证据要分开存档

问题做法：自动化、brief、召回、插件或第三方集成任务里，只要输出结构看起来合理，就顺手把“能力已经打通”也当成事实写下来。

正确做法：区分两种资产。用户给出的版式、语言、筛选口径，属于稳定偏好；真实数据链路、授权成功、插件可用、浏览器可连，属于执行证据。没有 tool-run 或 live proof 时，只能记录前者。遇到交互授权，则尽快把精确的 `verification_url` 或下一步动作交还用户继续。

教训：偏好可以复用，能力必须验真。把两者混在一起，后续 session 很容易误判现场状态。

### 11. 完成态按用户目标定义，不制造提交噪音

问题做法：把“提交一个分支”“推上去”机械理解成“必须新建 commit”，即使 worktree 已经没有 tracked diff。

正确做法：先检查 `git status -sb` 和远端状态。用户要的是可见的远端结果时，完成态可以是“当前 HEAD 上的分支已创建并推送”，不需要为了形式去制造空提交。本地运行产物如 `.playwright-mcp/`、`.local-stack-logs/` 默认留在工作树外。

教训：面向结果的 git 操作更干净，也更符合长期仓库卫生。

### 12. 任务合同只能有一个真源

问题做法：产品已经有 `Profile` / schema / quality gate 这类正式任务合同后，还保留一个默认 mounted skill 作为兜底能力，导致 UI 标签、模型指令和真实任务边界相互打架。

正确做法：先判断系统里谁才是任务合同的真源。对 Workspace 这类执行系统，`Profile` 应独占来源、工具、产物结构和质量门禁；默认 mounted skill 要 hard-cut，只保留用户主动添加的正交增强能力。历史数据则在读取、更新和 run 执行入口统一过滤，而不是只改某一层展示。

教训：当两个合同同时存在时，产品会先出现错误暗示，执行层再被旧逻辑带偏。稳定修复不是“换一个更准的默认值”，而是删掉多余合同。

### 13. 计数和门禁必须绑定原子单元

问题做法：把文件数、命中的来源条数、`有正文` 的 source 数或宽泛的 `usableReferenceCount` 当成复杂度、覆盖率或成功门槛。

正确做法：先定义真正的原子单元，再让计数、复杂度和 gate 都绑定到这个单元。对 context/skill 同步，应以 `skill` / `rule` 单元为准，而不是文件数；对检索/证据链路，应以 `source family`、`evidence role`、relevance 和 `attempted / matched / skipped / failed` 这类显式状态为准，而不是“数量够了”。

教训：指标口径一旦错了，UI 展示、fallback 逻辑和质量门禁会同时被污染。问题表面看像文案或排序，根上其实是资产模型和状态模型定义错了。

### 14. 本地调试绕过要做成环境边界

问题做法：本地调试遇到套餐、额度或商业门禁时，只在某个子路径关开关、加账号白名单，或者只改前端文案；结果一旦本地和生产共享数据库、队列或 runner，生产门禁仍会在真实链路里抢先触发。

正确做法：把“本地调试绕过”做成清晰的环境边界。后端统一返回稳定的机器原因码，如 `upgrade_required` / `llm_usage_quota`；Web 负责按 `resolvedLanguage` 显示中英文；`ENV_MODE=local` 要同时控制 quota enforcement 和任务 transport/runner ownership，确保任务真的走本地执行链路。

教训：本地 debug path 如果没有独立边界，只是把线上商业约束随机地移来移去。真正的修复是让 local mode 拥有完整、可验证的执行闭环。

### 15. Provenance 的信任边界要卡在持久化凭据

问题做法：接受模型自报的 URL、quote、`sourceType`、成功态或 Artifact 内容；provider 抓到原文但 clue 不匹配时直接丢弃快照；HTML 原文未经清洗就进入最终报告。

正确做法：把信任边界卡在已持久化的 planner / retrieval checkpoint 和 canonical receipt。任何 provenance 敏感字段都必须绑定真实 preflight/provider grounding；不满足就标记 `model_unverified` 并 fail closed。provider 抓取成功但暂时不能提升时，先保留原文快照；只有经过 dimension × role × period 复核的结果才能提升为正式证据或写入 Artifact。所有引用和报告 block 在 Artifact 边界统一转纯文本。

教训：这类系统的长期稳定性，不来自更多 prompt，而来自更窄的 trust boundary。

### 16. ID 合同出错时先修生成器，不要先扩列

问题做法：数据库报 `Data too long` 之类错误时，先扩 `VARCHAR`、放宽 schema 或新增一次性兼容迁移，把上游 ID 合同问题藏起来。

正确做法：先核对列宽、ID namespace 和生成器的原始设计，再修上游生成逻辑。像 `goal_revision_id` 这类统一业务 ID，应维持稳定长度合同，用确定性派生或新的安全命名空间修复，而不是让不同入口各自生成不同长度的 ID。

教训：扩列能让当前写入通过，但会把不一致的 ID 语义扩散到更多表和更多服务里。

### 17. 兜底路径不能抢主路径

问题做法：系统已经拿到 Writer 生成的完整 `ReportDocument`，却仍然无条件丢弃主文档，只从 Evidence Ledger 确定性拼出“摘要 + 关键事实”骨架，把 fallback 反过来变成主交付。

正确做法：完整 `ReportDocument` 是用户交付主路径。确定性投影和事实骨架只在 Writer 超时、失败或缺失时做兜底；一旦主文档可用，Web、Backend 和 ML 都应围绕它继续补引用、补定位和补验证，而不是重建另一份简化版报告。

教训：fallback 的职责是兜底，不是接管。主路径和兜底路径一旦反转，产品会在“看起来更可控”的同时丢掉真正的任务完成度。

### 18. 引用展示和原页定位必须继承既有交互合同

问题做法：为了补溯源，把报告里的引用改成孤立的 `[1][2][3]` 编号按钮，再用新的弹窗或直接 `window.open(canonicalUrl)` 代替原有来源查看器。

正确做法：报告正文保持完整内容，并在对应事实旁放可读的来源引用。点击引用后复用既有 Source / Artifact 页面、viewer 和 locator，在原页面定位到具体段落、页码或表格单元；弹窗最多做预览，不能成为唯一溯源路径。

教训：溯源增强不能以破坏阅读路径和交互一致性为代价。对这类产品，引用的可读性和原页定位能力本身就是交付合同的一部分。

### 19. 显式 Task 问题要按用户边界冻结，不做模型改写

问题做法：把用户多问任务合并成一整段 instruction，再由系统或模型自行改写、拆分或重命名 question，导致 `questionId`、`sourceSpan` 和逐问完成状态都不稳定。

正确做法：对用户显式枚举的问题、问句或逐项要求，按原句边界冻结成多个 task question，并为每个问题生成稳定 ID 与 `sourceSpan`。后续 Need、Claim、Gap、completion gate 和 UI 展示都按逐问粒度核对，不把多问任务重新揉成一段 prompt。

教训：任务合同的最小原子单元是“用户显式提出的问题”，不是整段 instruction。原子边界一旦丢失，后面的完成判定和补强路径都会变模糊。

### 20. 完成 Gate 依赖 Backend 持久化 Need 终态，不让 ML 自行猜

问题做法：ML 只根据 Evidence Item 数量、原始检索草稿或“是否拿到部分证据”来判断问题是否回答完整，于是把 `partial_exhausted` 一类“有部分答案但检索已穷尽”的状态误判成完整回答。

正确做法：检索完成后，由 Backend 冻结并持久化每个 Need 的终态及其 hash，再把这份投影作为 ML 的依赖输入。`complete_with_gaps`、`answered_with_gap`、`unable_to_answer` 这类状态都应建立在 Backend 已验证、已持久化的 Need outcome 上；缺少终态时要 fail closed。

教训：完成 Gate 属于控制平面的职责。模型可以写解释，但不能自己猜最终完成态。

### 21. 时间窗类 automation 先锁任务环境日期，再扫证据

问题做法：做“今天”“过去 24 小时”“晨间简报”这类任务时，直接沿用机器当前时钟、宽泛的最近修改时间或模糊的“当天”概念，导致证据窗口和任务上下文日期错位。

正确做法：先读 automation 提供的 `current_date`、任务环境日期、上次运行时间或显式时间范围，把“今天 / 昨天 / 过去 24 小时”先转成绝对日期窗口，再围绕这个窗口扫描 `git log`、文档 diff、最近修改文件和外部数据源。需要给用户澄清时间时，直接写出具体日期。

教训：时间窗先漂移，后面的证据筛选、工作回顾和 briefing 都会一起失真。

### 22. 先锁产品类别，再谈市场与竞品

问题做法：用户在探索方向时，还没分清 workflow tool、analysis tool、recommendation tool，就直接滑向“AI stock assistant”“市场够不够大”或“有没有竞品”这类宽泛讨论，导致竞品集、合规约束和产品叙事全部跑偏。

正确做法：先把产品类别锁清楚，再做市场判断。对“金融投研”默认先确认它是 research workflow / evidence management / briefing system，还是 buy/sell recommendation engine；对“1 个人 + Codex 能 cover”的方向，再看一个人能否覆盖实现、测试、部署和交付验证。

教训：产品类别一旦判错，后面的功能边界、竞品地图、风险判断和语言 framing 都会一起错。

### 23. 手工路径一旦跑通，就先收口成合同

问题做法：一次性手工路径已经验证可行后，只停留在“这事能做”，没有及时把输入、输出、失败状态、清理动作和隐私边界写清楚；后续一讨论 Skill、插件或网页形态，就又回到模糊描述。

正确做法：手工路径一旦跑通，立刻收口成最小合同：输入是什么，产物是什么，哪些状态算成功/需登录/CAPTCHA/未发现资源/签名失效，临时资源怎样清理，哪些数据绝不持久化。合同收稳后，再决定它该落成 Skill、本地 helper、浏览器插件还是 Web 控制台。

教训：产品化的第一步不是“包个壳”，而是把一次性能力变成可重复执行的合同。

### 24. 竞品与开源评估先跑同链路，再查 license

问题做法：只看竞品首页、README、stars 或功能列表就下产品判断，忽略真实登录门槛、失败状态、交付形态和许可证边界。

正确做法：先用用户给出的同一个链接、同一种任务或同一条输入链路去实测竞品，再核对 GitHub license、闭源兼容性、复用边界和合规成本。没有同链路体验和 license 核验，就不给产品结论。

教训：营销文案解释不了真实摩擦，stars 也解释不了复用边界。

### 25. 发布与版本脚本先读包装层，不把 `--help` 当无副作用探针

问题做法：面对公司内部的 `publish` / `mono-publish` / `changeset_dev` 一类脚本时，直接运行 `--help`、空参数或“试一下”命令，默认它们只会打印说明。

正确做法：先读 `package.json`、脚本包装层和仓库文档，确认真实入口、主干分支、changeset 消费方式、tag 约定和是否存在副作用。没有明确的 dry-run / status 子命令时，先用 `git`、tag、changeset 文件和远端状态做只读判断，再决定是否执行真正的发布命令。

教训：内部 CLI 不一定遵循通用约定。把 `--help` 当安全探针，可能直接触发真实发布。

### 26. 格式支持要精确到持久化包装层，而不是停在“支持 Markdown”

问题做法：看到系统声称“支持 Markdown”或“兼容历史内容”后，只按理想输入设计兼容层，比如只识别裸 Markdown 表格，忽略 `<p>`、`<div>`、`<br>`、`<pre><code class="language-markdown">` 这类真实持久化包装层。

正确做法：围绕真实链路定义格式合同：粘贴、编辑器预览、保存 payload、接口返回、客户端渲染分别会产出什么形态；把每一层真实 wrapper 都列入兼容矩阵，并用真实 payload 建回归测试。需要兼容时，也要同时检查“历史数据重新打开编辑”和“消费端直接展示”这两条回流路径。

教训：语法支持是抽象说法，真正决定是否生效的是落库和回放时的具体 shape。

### 27. Recurring automation 的记忆续跑点必须绑到精确路径

问题做法：周期任务只记得“要写 memory”，却默认写到通用目录、错误 automation id，或者因为文件不存在就跳过写回。

正确做法：优先使用用户或系统给出的精确 `Automation ID` 和 memory 路径；文件存在就先读，不存在就创建在该路径。续跑摘要至少要写清：上次窗口锚点、本轮实际读取范围、关键新增规则、空数据源与未纳入证据的来源，以及本次运行时间。

教训：周期任务的连续性不是来自 prompt，而是来自稳定、可追溯的 continuation point。

### 28. 能力现状要分清 documented、installed、runnable 三个状态

问题做法：看到仓库里有 workflow 文档、磁盘上有 skill 目录、或者下载接口返回了某个版本号，就把能力直接当成“已经可用”。

正确做法：把现状拆成三层分别核验。`documented` 看规则、设计稿和约定目录；`installed` 看文件是否真正落盘、入口是否可被 Codex 识别、包内元数据与请求版本是否一致；`runnable` 则继续核对二进制、依赖、模型、预期输出目录和最小 smoke。最终汇报时只声明已经被当前证据覆盖到的那一层。

教训：文档存在、文件存在和能力可运行是三件不同的事。混成一个状态，后续 session 就会高估现场能力。

### 29. 必读长文不能把工具输出截断当成“已经读完”

问题做法：把多份长规则文件一次性并行打印后，只看到首段输出，就默认自己已经完成了“必须先读”的前置动作。

正确做法：先用 `wc -l` 或等价方式确认长度，再按行段或分页补读到 EOF。只要工具输出发生截断，就继续读取缺失部分，直到能明确说明哪些文件已完整审阅、哪些还没有。

教训：对这类 workspace，前置规则本身就是执行合同。长文档截断后不补读，等于在错误前提上继续工作。

### 30. 本机 symptom 消失时，先确认是上游修复还是本地 workaround 在遮蔽

问题做法：看到公开 issue 在本机没有复现，就直接把结论写成“问题已经好了”。

正确做法：继续检查本机是否存在 trigger、feature flag、代理、拦截器、版本分叉或历史补丁，先解释 symptom 为什么没有出现。若只是本地 workaround 生效，就明确写成“本机已缓解，上游未确认修复”，并同时记录保护收益和观测代价。

教训：本地无症状不等于上游无问题。把“已缓解”和“已修复”混为一谈，会误导后续排障和升级判断。

### 31. worktree 是显式隔离工具，不是默认逃生舱

问题做法：一看到主工作树有未提交改动，就擅自切到 worktree，或者反过来在用户明确要求隔离修复时仍直接在主树动手。

正确做法：先检查主工作树状态和用户边界。只有当用户明确要求类似“单间一个 worktree 修复用户反馈”时，才从相关 mainline 创建独立分支和 worktree；否则默认留在当前工作树内，小心避开无关脏改动。

教训：worktree 解决的是隔离边界，不是思考偷懒。是否启用 worktree，本身也是需要尊重的产品/协作约束。

### 32. 用户给出完整安装命令时，执行指定目标，但补齐安装完整性核验

问题做法：用户给了明确安装命令后，只照抄执行并以“目录里有 `SKILL.md`”收尾，忽略压缩包安全、frontmatter、引用文件和清理细节。

正确做法：按用户给定目标路径执行安装，同时额外核对 ZIP 完整性、路径穿越、符号链接、`SKILL.md` frontmatter、请求版本、最终落盘状态，以及 `references/`、`scripts/`、模板等被主文件引用的辅助资源是否齐全。临时文件清理也应使用当前系统真实存在、作用域精确的命令。

教训：显式安装命令解决的是“装到哪儿”，不是“装得是否完整可用”。主文件落盘不等于整个 Skill 资产可用。

### 33. 专名数据修复先做局部覆盖，不做单字全局替换

问题做法：遇到地名、多音字、地方读音或领域专名错误后，直接把某个字的默认读音全局替换，试图一次性“修干净”。

正确做法：按“城市或域 + 完整实体名”建立局部覆盖，只修改已经有证据的专名项。像宁波“隘”的读音修复，应覆盖 `邱隘东`、`邬隘`、`柳隘`、`曹隘` 这些完整站名，而不是把所有“隘”都改成同一个读音。

教训：专名问题表面像字典问题，实际是上下文问题。局部覆盖比全局替换更接近真实世界，也更不容易误伤别处。

### 34. 快照型数据要先做可复现性，再把“已刷新”当完成

问题做法：数据同步脚本能跑通、页面能加载新结果后，就把任务标成完成，忽略同一份原始输入是否会生成不同输出。

正确做法：对静态快照、导入脚本和离线构建产物，额外核对重复生成的字节级稳定性。若差异只来自 `generatedAt` 之类运行时字段，应把它绑定到源快照时间或固定输入版本，再验证 hash 稳定、测试通过、线上产物一致。

教训：能生成和可复现是两层不同的完成态。没有可复现性，后续审计、回滚和差异判断都会变得不可信。

### 35. 公开资料归档先拿完整真源，再做翻译或总结

问题做法：看到公开页面能打开，就直接基于 HTML 首屏或目录页翻译、总结和落库，忽略正文分页、折叠区块和失效媒体链接。

正确做法：先验证展示页是不是完整真源。若 HTML 只有目录、首段或缓存残片，就继续查公开数据接口、分页 cursor 和签名媒体 URL，拿到完整原文快照后再翻译、归档和做本地链接校验。无法读取的区块要明确标缺，时效性事实要标成“保留原说法，未重新核验”。

教训：公开页面“能看”不等于“可完整归档”。先拿全量真源，后面的翻译、引用和素材落库才可信。

### 36. 清理类任务先把“候选空间”和“安全删除范围”拆开

问题做法：`dry-run` 给出一个可释放总量后，就把它当成安全收益，或者在扫描还不完整时继续执行删除。

正确做法：先只做 `dry-run`，再把纯 cache、medium-risk 数据、回收站、快照、旧工具和应用状态分开报告。对正在运行的 app、需要 `sudo` 的系统目录和长时间卡住的阶段，明确标记为“扫描不完整/部分跳过”；真正删除前，让用户关闭相关应用并确认范围。

教训：清理工具给的是候选集，不是授权后的删除单。把二者混为一谈，很容易误删仍有价值的数据。

### 37. Workspace 回顾不能只看根仓库，必须扫描内嵌独立 repo

问题做法：做“过去 24 小时做了什么”时，只看根仓库 commit 或根目录 mtime，于是把子项目里的真实工作判成“没有足够痕迹”。

正确做法：先用绝对时间窗锁定范围，再检查 workspace 内的独立 Git 仓库、子项目目录和按时间过滤的文件变更，同时排除 `.git`、构建产物、部署缓存等噪声。根仓库没有新 commit，不能证明整个平台没有活动。

教训：workspace 是容器，不是单仓库。回顾类 automation 如果不扫子仓库，证据会系统性漏报。

### 38. 专用文档入口比浏览器近似读取更可靠

问题做法：看到内部或专用文档链接就直接用浏览器打开，默认网页首屏就是完整真源。

正确做法：如果仓库规则或历史经验已经给出专用入口，例如 `docs.xiaohongshu.com` 的 redoc / `hi docs:get`，先走它拿正文、hash 和 sourcemap，再决定是否需要浏览器补验。若 INDEX 或 skill 路径不存在，先验证真实路径并记录缺口，再回退到搜索或只读工具。

教训：文档系统的专用读取链路自带版本和结构信息；浏览器只适合补验，不适合作为默认真源。

### 39. 陌生仓库里的便捷命令可能暗带包管理器副作用

问题做法：在不熟的仓库里直接跑 `pnpm exec`、`pnpm build` 或包装 CLI，默认它们只是执行当前命令。

正确做法：先看 `packageManager`、本地二进制和包装层。能直接用已有可执行文件就不要额外触发 Corepack、依赖重装或内部 CLI 自动升级；若误触发了 `package.json` / lockfile 变更，先识别哪些是工具链副作用，再恢复到任务需要的干净基线。

教训：很多“只是跑一下”的命令会改依赖图、锁文件和 CLI 版本，副作用本身就会污染问题判断。

### 40. 代码搜索负责定位主线，远端 Git 负责验证分支真相

问题做法：把 code-search 的无结果直接解释成“代码不存在”，或者在 `--single-branch` clone 里直接跟踪其他远端分支。

正确做法：先用 code-search 定位主分支线索；一旦问题落在未合入的 feature branch，就立刻改用 `git ls-remote`、临时 clone/fetch 和 `git diff`。对于 `--single-branch` 克隆，先检查 `remote.origin.fetch`、`git show-ref` 和当前干净 HEAD；若切分支失败并写入大量伪改动，先恢复到记录的 HEAD，再补 refspec。

教训：搜索索引、远端引用和本地工作树是三个不同层面。把它们混成一个“代码是否存在”的判断，最容易误操作。

### 41. MCP / Skill 缺席要分层诊断，不把当前任务视图当成唯一事实

问题做法：当前任务里看不到 MCP 工具或某个 skill 路径，就立刻改配置或断言它没启用。

正确做法：把问题拆成四层：`documented`、`installed/configured`、`process/handshake healthy`、`task-visible`。MCP 先查 `config.toml` 和 CLI 状态，再用 `initialize` / `tools/list` 验证协议握手；都正常时，把“当前任务未显示”视为 task snapshot 问题，重启 Codex 并新建任务复验。项目级 skill 则先验证 INDEX 指向的真实路径是否存在，缺失就明确记录并回退。

教训：当前任务看到什么，只是现场快照。它既不能替代配置真相，也不能替代文件系统真相。

### 42. 旧工具链项目的环境合同以运行时真相为准

问题做法：看到旧仓库同时存在 `.nvmrc`、README、`package.json`、pnpm 痕迹和历史 CLI 后，直接选一个看起来新的工具链，或者试图局部补一个缺失依赖。

正确做法：先用 `.nvmrc`、lockfile、实际可运行的 CLI、bundle 请求和依赖解析结果重建环境合同，再回写 README 与 `package.json`。像旧版 Metro/Hammer 这类链路，若运行时只能稳定支持 npm 平铺 `node_modules`，就不要继续沿 pnpm 符号链接布局试错，也不要把“缺哪个包装哪个”当修复。

教训：旧项目里最可靠的事实，不是文档自述，而是成功跑通的运行时组合。

### 43. “上下文沉淀”默认指修改局部的业务文档，不是组织知识体系

问题做法：用户提到“迁移上下文方案”“把隔壁方案拿过来”时，默认理解成 `org-knowledge`、`org-spec` 或统一知识库改造，于是把任务做成体系迁移而不是修改后的上下文沉淀。

正确做法：先确认用户要的是哪一类上下文。若用户说的是“针对代码修改后的业务上下文沉淀”，就把落点收敛到模块 README、`docs/<topic>.md`、`CHANGELOG.md` 这类最小职责文档，并尊重仓库现有的可跟踪规则文件约定，例如保留已纳入版本控制的 `AGENT.md`，而不是强推通用的 `AGENTS.md` 命名。

教训：上下文方案首先是协作合同，不是名词统一。理解错任务边界，后面的文档结构和工具动作都会偏。

### 44. 精确回滚要覆盖工具副作用，并用工具自身状态验空

问题做法：用户说“还原所有更改”后，只恢复 tracked 文件 diff，忽略 `ctx install` 一类工具顺手生成的 `.mcp.json`、IDE 目录和本地资产，或者直接用 `reset --hard` 一把清空。

正确做法：把回滚目标拆成三类分别处理：tracked 文件恢复、任务期间新增文档删除、工具生成资产清理。最后除了 `git diff` / `git status`，还要补跑工具自己的状态命令，例如 `ctx installed`，确认已经回到“未安装/无新增资产”的基线，同时保留任务开始前就存在的用户改动。

教训：精确回滚的难点不在 Git，而在副作用边界。只有把工具自己的状态也验空，才能证明真的回到了任务起点。

### 45. 埋点验收要核对发送前标准报文，而不是停在代码和平台配置

问题做法：看见业务代码里调用了 tracker、Meta 平台上也有点位定义，就把“点位存在”当成“真机已正确上报”，或者只核对业务层 `push` 参数，不看 SDK 发送前补齐的上下文。

正确做法：把埋点验收拉到 payload 层。除了核对点位定义、字段名和页面代码，还要在开发环境打开发送前日志，抓到类似 `asgard-plugin-tracker before send` 的完整标准报文，逐项核对 `context.user_id`、`context.group_user_id`、`event_info.page_key`、`module_key`、`action` 和 `attributes`。没有拿到这份报文前，只能说“链路已打开，真机发送待验证”。

教训：埋点真正容易出错的地方，往往在 SDK 补齐上下文和真实发送阶段，而不是业务代码那一行 `push`。

### 46. 跨分支合并时，业务改动和目标分支环境合同要分开处理

问题做法：把源分支的 `README`、`.nvmrc`、`package.json`、lockfile 和工具链约束一起带进目标分支，或者在主工作区直接 merge，结果把目标分支已有运行时基线冲掉。

正确做法：先用 `git ls-remote` 锁定源分支和目标分支的远端 SHA，再在隔离 worktree 中合并。冲突出现后，把“业务改动”和“目标分支环境合同”拆开判断：业务代码按用户目标合并，运行时约束继续以目标分支当前的 `README`、`.nvmrc`、`package.json`、lockfile 和构建脚本为准。最后再用 focused test、`git diff --cached --check` 和远端 SHA 验证“功能已带入、环境没回退”。

教训：跨分支 merge 的目标是迁移 feature，不是把源分支的整套工具链历史倒灌到目标分支。

### 47. SDK 的 `Network Error` 先判定是不是传输层无响应

问题做法：看到 tracker 或 SDK 报 `Network Error` 后，直接去查业务埋点参数、平台点位、接口 4xx/5xx、`user_id` 映射，或者把它当成 payload 错误。

正确做法：先读 SDK 日志和实现，确认这个错误到底表示什么。像 RN XHR 的 `onerror` 场景，本质是没有拿到 HTTP 状态码，优先排查设备代理、HTTPS 拦截、证书链和 Chrome remote debugging 对 Native Module 的影响。只有当 `asgard-plugin-tracker before send` 与 `post track data success` 都出现后，payload 级验收才有意义。

教训：链路还没到 HTTP 响应，业务参数讨论就没有诊断价值。先把传输层打通，再谈 payload 和入库。

### 48. 发布前检查要把真实阻塞和仓库噪声分层

问题做法：只要 lint、test、build 或脚本报错，就统一写成“当前版本不能发”，把仓库既有错误、Node 版本不兼容、流程硬门禁和本次改动回归混成一类。

正确做法：先按目标分支和发布 SOP 重建检查环境，再把结果拆成四层：本次改动回归、仓库既有噪声、运行时/工具链不兼容、以及 changeset / 分支 / tag / 平台状态这类流程硬门禁。只有和当前发布合同直接冲突的项，才算真正阻塞；其他项要单独记录，不污染本次发布结论。

教训：发布检查的价值是帮助决策，不是堆报错清单。分层归因之后，用户才能判断是该修当前改动、切换运行时，还是按 SOP 继续推进。

### 49. 学习型产品先锁能力模型和证据，再扩玩法

问题做法：一开始就围绕世界观、角色、商城、收集或“提升综合能力”做产品设计，却没有定义首版究竟训练什么能力、怎样观察到它、什么算成功。

正确做法：先把首版能力模型、最小事件、提示阶梯和垂直切片成功标准写清楚，再决定视觉包装和外围系统。像 `水岛` 这类 6-8 岁学习产品，先锁 `空间关系 → 旋转 → 路径规划 → 因果修正 → 近迁移`，再规定哪些行为日志能支持家长证据卡，哪些能力暂时不能宣称。

教训：学习产品的第一性原理不是“好不好玩”，而是“有没有可观察的学习证据”。能力模型没站稳时，扩玩法只会把验证口径弄乱。

### 50. 生态调研先分清衍生关系，再谈复用和规模

问题做法：看到一批视觉相近或都提到同一个项目的仓库，就直接统称为“衍生产品”，顺手把官方收录、直接依赖、跨端移植和纯风格借鉴混成一个生态。

正确做法：先从上游 README、官方 `Usage Cases`、`package.json`、运行入口和 license 建立关系分层。区分“官方列出的案例”“直接依赖上游包”“自行移植到别的技术栈”“只借鉴视觉语言”这几类，再讨论生态广度、商业限制和可复用边界。

教训：生态规模不是数长得像的项目，而是数真实依赖关系和授权边界。关系类型一混，调研结论就会失真。

### 51. 浏览器端本地视觉核验，要把推理位置、联网行为和隐私结论拆开

问题做法：看到页面用摄像头、模型跑在浏览器里，就直接写成“完全本地、不联网、不会上传摄像头画面”，或者反过来只要页面还有排行榜 / 统计请求，就断定视觉推理不是端侧完成。

正确做法：把三个问题拆开回答。第一，模型推理是否在浏览器端完成；第二，页面是否还会联网加载资源、提交分数或上报统计；第三，是否存在媒体帧上传。前两项可以通过静态代码链路判定；第三项若要下强结论，必须在用户授权摄像头后抓取完整 Network payload，不能拿静态代码审计替代。

教训：浏览器端 AI 的“本地推理”与“完全离线”不是同一句话。隐私结论必须跟证据层级对齐。

### 52. 周期复盘遇到空增量时，刷新索引，不制造新经验

问题做法：上次运行之后只新增了上一轮 review 自身和当前执行会话，却仍把旧结论重新包装成“新增经验”，让文档长度继续增长，但没有新的信息增量。

正确做法：先锁增量时间窗，再把候选 rollout 分成“业务任务”“上一轮 review”“当前运行”三类。若窗口内没有新的业务任务样本，就只刷新 live 索引、空窗说明、未读来源和 automation memory；只有出现新的失败模式、偏好信号或高风险验证路径时，才扩写正文和规则编号。

教训：周期复盘的价值在于压缩噪声、维持 continuation point，而不是机械地每轮追加新条目。

### 53. 内部发布术语先映射到真实平台对象

问题做法：把“Beta 个人页”“发 beta”“个人泳道”这类内部 shorthand 按字面猜成某个熟悉脚本，先跑 RN `build:test`、分支包或别的错误发布动作。

正确做法：先把术语映射到真实平台对象。要先确认它指的是 RN 分支包、后端 PBeta/ONES 个人泳道、PC 个人页域名，还是 Apollo / Edith / IDL 同步链路。用户一旦纠正，就立即停止错误路径，围绕真实目标重新组织提交、发布和验收。

教训：内部发布词汇描述的是平台对象，不是自然语言近义词。对象没锁清之前，任何 build 或 deploy 都可能在错误系统上制造噪声。

### 54. 私有 skill / CLI 的 401 要把认证、依赖和定位链路一起修

问题做法：看到 401 就临时把 token 写进 shell、仓库或 `.env`，或者只补一个 header 后就宣布工具“能用了”。

正确做法：把问题拆成三层验证：认证头和凭证来源是否正确、运行时依赖是否齐全、workspace / skill 发现链路是否能定位到目标。修通后，把凭证放到 Keychain 之类的系统密钥库，再补一次真实只读 smoke，不把临时环境变量当长期方案。

教训：工具鉴权问题通常不是单点故障。只有认证、运行时和定位链路一起闭环，skill 才算真正恢复可用。

### 55. 高影响外部操作先把停用范围锁到最小可验证单元

问题做法：用户说“把结算关了”“停掉这个服务”之类高影响操作时，直接对最上层账号、billing account 或整组资源动手，没有先拆清真正目标是“停止继续计费”还是“彻底关闭账户”。

正确做法：先做只读盘点，确认当前账号下有哪些真实绑定对象，再把用户目标收敛成最小可验证单元，例如项目级 unlink 而不是账户级关闭。执行前说明残余费用与服务降级影响，执行后逐个目标回读状态，确认没有遗漏。

教训：同一句自然语言在云平台里可能对应完全不同的 blast radius。先缩范围，再执行，才是安全的默认动作。

### 56. 分支 SNAPSHOT 编译通过，不代表正式制品已经等价

问题做法：跨仓发布时，看到上游分支 `SNAPSHOT` 能编译、接口文档也更新了，就默认 tag 后生成的正式制品一定包含同样字段或方法，直接推进下游依赖替换、CR 和主干发布。

正确做法：tag 和制品发布之后，必须从正式仓库重新解析官方产物，再用最小内容回读或下游编译验证确认字段、方法和兼容性真的存在。只要正式制品与分支 `SNAPSHOT` 不一致，就立刻停在 promotion 边界，先追溯源分支、主干和制品仓之间的漂移，不绕过编译门禁。

教训：源码、分支制品和正式制品是三层不同证据。没有正式产物回读，跨仓发布闭环就还没成立。

## 二、徐昊偏好与理念档案

### UI 设计偏好

- 偏好真实、密度合适、可重复使用的工作界面。SaaS、CRM、运营工具应安静、克制、可扫描，避免营销式 hero、装饰性卡片堆叠和单一色相氛围。
- 文案必须精确，尤其是状态、CTA、错误、disabled、expired、互斥关系和 backend display text。用户给出明确文案时应原样落实。
- 错误文案应由展示层按当前语言环境映射，不把某一种自然语言硬编码进后端稳定错误合同。
- 图标语义要准确。工具按钮优先使用熟悉符号和已有 icon library，不用文字胶囊替代常见图标。
- 引用应贴在对应事实旁，并尽量显示可读的来源文字或来源名；用户不接受把完整报告降级成抽象数字脚注。
- UI 状态不能只靠“看起来差不多”。需要验证移动端和桌面端的文本容器、布局重排、重叠、加载态、空态和错误态。
- 临时 mock 只用于验证，验证后立刻删除，不能留下会误提交的开关。
- 参考站复刻或个人资料页任务里，核心交互语言要尽量贴近参考站；未确认的个人信息、项目内容和外链应留空，不靠推断补满。

### 产品设计理念

- 产品壳层和真实能力要对齐。未上线或未准备好的能力宁可 hard-cut，也不要制造可点击但不可用的假入口。
- AI 产品设计要区分“感知层”和“真实执行层”。前台可以用用户理解的比例和状态，后台必须保留真实成本、token、模型、source、artifact、checkpoint 等可审计数据。
- AI 内容生成器或内容 Skill 的价值，先按“结构脚手架”评估，不把格式完整、标题变多或 CTA 齐全当成增长策略已经成立。
- 学习型产品先定义第一能力模型、最小行为证据和迁移验证，再扩世界观、收集、商城或泛能力宣传。没有观察指标前，不宣称“提升系统思维”这类宽泛效果。
- “上下文沉淀”默认指修改后的业务规则、状态流、接口契约和问题处置文档，不指向单独的 org-knowledge 体系。用户要的是变更上下文被留下，而不是再造一个知识平台。
- Workspace / agent 类产品的价值在于上下文、来源、产物、记忆和可续接运行，而不只是一个聊天框。
- 对“1 个人 + Codex 能 cover”的方向，判断标准是一个人能否覆盖实现、测试、部署和 live 验收，而不是只看 Codex 能不能把代码写出来。
- 一旦已有 `Profile`、schema 或 run contract 这种正式任务合同，它就应成为唯一真源；默认 mounted skill 只适合用户显式选择的正交增强，不适合做兜底任务定义。
- 完整 `ReportDocument` 是报告类产物的主交付；Evidence Ledger、确定性投影和 renderer 负责验证、渲染与兜底，不负责把主文档替换成简化骨架。
- 首页推荐、任务入口和 briefing 需要具体到公司、行业、资产范围或明确目标，泛泛推荐没有决策价值。
- 当用户说“展示内容不对”时，尤其是 memory / goal / context 这类界面，默认问题在真实数据分层、revision/version 语义或 durable context pack，而不只是标签文案。
- 复杂度、资产数和 coverage 这类产品指标，应该展示原子单元，并把 `unit_count` 与底层 `file_entry_count` 之类实现细节分开。
- 一次性手工能力如果要继续做成 Skill、插件或网页，先写清输入、输出、失败态、清理动作和隐私边界，再讨论外壳形态。
- 生态或竞品调研里，先区分官方收录、直接依赖、跨端移植和纯风格借鉴，再判断生态规模、商业价值和复用边界；license 必须以一手仓库真源为准。
- “支持某种格式”必须落实成精确合同：支持哪些 grammar、哪些 wrapper、哪种持久化 shape、哪些预览和消费入口。用户不接受只写“支持 Markdown”这种泛化承诺。
- 金融方向默认 framing 为“金融投研工作流工具”：任务拆解、来源计划、证据核验、报告装配、版本化与增量更新。除非用户明确要求，不把它说成 stock-picking、buy/sell 或 recommendation 产品。

### 交互原则

- 直接执行优先。用户说“改吧”“跑一下”“merge进去”“写到 AGENTS.md”时，默认推进到实现、验证、文档回填，不停在解释层。
- 该问时问，但先自己查。只有答案无法从本地上下文发现，并且错误假设会造成风险时再问。
- 回答要短、直接、有判断。不要客套，不要用“好问题”“乐意效劳”，不要用漂亮但空的判断词。
- 对用户的纠正要转成长期规则。尤其是文案、图标、状态、mock 回收、验证方式、兼容边界和测试要求。
- 内部发布 shorthand 要先确认它指的是哪一层真实对象。像“Beta 个人页”这种说法，默认先分清 RN 分支包、后端 PBeta 个人泳道和页面域名，再动脚本。
- 用户说“不要 org-knowledge”“针对修改后的上下文沉淀”时，按字面收窄任务边界：优先沉淀变更相关文档、规则和回滚约束，不扩展成组织知识工程。
- 内容创作任务先锁交付范围和账号定位。用户只要一篇，就只交一篇；先收真实素材、真实经历和发布边界，再决定标题、CTA 和封面。
- Build in Public 相关任务，先把真实进度、已验证证据和“这件事改变了什么判断”收拢成同一事实真源，再按平台改写。X 更适合“判断 + 数字 + 因果”，小红书更适合“起因 + 阶段里程碑 + 可感知画面 + 邀请参与”。
- 外部文章任务里，“翻译和落库”默认包含中文译文、英文原文快照、本地素材归档和缺失/未核验内容标注；不接受只在对话里给摘要。
- 用户要求“试试这个竞品 / 这个链接 / GitHub 能不能复用”时，先做同链路实测和 license 核验，再讨论差异化或商业化。
- 用户明确说“不要帮我点 CR / 审批”时，停在代码、编译、提交、推送和剩余门禁状态，把准确的 CR 链接、阻塞人和下一步动作交还用户；不要越过人工审批边界。
- 用户说“我重启了，你重新验收吧”时，要把它理解为一次 fresh acceptance request，而不是让你复述上一轮结果。
- 晨间简报、工作回顾和“今天 / 过去 24 小时”这类请求，先固定任务环境日期和证据窗口；证据不足时直接写明，不用推断补满。
- 用户点明已有某个 skill 或文档入口时，先验证它的真实路径和可用性，再决定是否回退到浏览器或普通搜索。
- 讲架构或代码库时，要按对方角色已有的心智模型组织解释。面对前端工程师，优先从请求入口、异步状态、接口合同、缓存和外部依赖讲起，而不是直接堆后端分层术语。

### 工程验证偏好

- 浏览器、插件、Chrome extension、MCP 或页面壳层异常时，先把底层服务和系统基线拉到健康状态，再做 UI/交互验收。
- 用户主动改变一个环境变量后，偏好单变量复测。关掉后台隧道、停用一个过滤器、重启机器之后，都要重采 baseline。
- 不接受“组件都装着”“扩展看起来 enabled”“命令能跑 `--help`”这种弱证据。用户更看重真正连通、真正可用、真正通过测试的闭环。
- 自动化和集成类任务里，没有执行证据时只能沉淀输出格式和口径，不能顺手暗示能力已经接通。
- 私有 CLI / skill 的鉴权修复，偏好把凭证放系统密钥库并补真实只读 smoke；不接受把 token 留在仓库、聊天或长期 `.env` 里当捷径。
- 本地调试类修复，偏好真实队列/数据库/浏览器闭环验证；配置值显示正确不等于执行路径真的已经切到 local。
- 当用户说 dev / local 模式“不生效”时，先核对真实请求走向的 `baseURL`、环境开关和返回 payload；环境名不等于数据源已经切走。
- 跨分支 merge、cherry-pick 或补丁回植时，偏好保住目标分支自己的运行时基线；业务改动能迁进来，不代表 Node/npm/lockfile 也该一起迁进来。
- 做跨仓 IDL / artifact promotion 时，偏好同时验证源码、正式制品仓库解析和下游最小编译；分支 `SNAPSHOT` 的成功不能替代正式版本验证。
- 涉及埋点或 tracker 调试时，偏好拿到真机触发后的完整发送前报文，直接核对 `user_id`、页面键和属性字段；代码调用、平台点位和 CLI 查询都不足以替代 payload 级验收。
- tracker / SDK 报 `Network Error` 时，偏好先确认是否压根没有 HTTP 响应，再排查代理、TLS 证书和 remote debugging；链路打通之后才进入 payload 验收。
- 当只读 SQL、repo、本地文件时间戳或已登录浏览器已经足够回答问题时，优先走这条最短真源路径，不为修 connector 或 browser runtime 偏离主问题。
- 内容兼容修复要优先用真实接口响应回放；尤其是 `<pre><code>`、富文本清洗和历史 wrapper 这类格式问题，不接受只在理想化 fixture 上通过。
- 危险清理、磁盘回收和系统瘦身任务，偏好先做 `dry-run`，再把纯 cache、medium-risk 数据和运行中 app 导致的漏扫范围分开说明；未确认前不执行删除。
- 地名、读音、地域专名或映射数据修复时，偏好官方/运营方/本地证据加完整实体覆盖，不接受按词典音或单字规则机械批量替换。
- 对 `complete_with_gaps`、`answered_with_gap` 一类状态，偏好逐问核对 Backend 持久化 Need 终态，不接受模型只按 Evidence Item 数量或部分证据自行判定完成。
- 对 workflow、skill、CLI 或录屏/转写工具的现状判断，偏好把 `documented`、`installed`、`runnable` 三层拆开报告；安装路径或 README 不能替代可执行验证。
- 对内部文档系统，偏好先走 canonical CLI / skill，再用浏览器补验；网页首屏和近似抓取不能代替带 hash / sourcemap 的正式入口。
- 在陌生仓库里，偏好先看命令包装层和包管理器副作用边界，再运行 `pnpm exec`、构建 CLI 或自动升级工具。
- 判断 MCP / skill 可用性时，偏好分开验证配置、协议握手与当前任务可见性；当前会话缺席不等于没启用。
- 当本机没有复现公开 bug 时，偏好继续追查本地 trigger、拦截器、feature flag 或历史 workaround；“当前被遮蔽”与“上游已修复”必须分开表述。
- 做 workspace 范围的工作回顾、briefing 或进展追踪时，偏好同时检查内嵌独立 Git repo 和绝对时间窗内的文件变更，不把根仓库静默误判成“没有工作”。
- 只做静态源码、POM、文档和配置核对时，偏好明确标注这是静态验证层，不把结构分析、接口计数或源码路径写成 build、smoke 或运行链路已经验证。
- 浏览器端 AI / 视觉隐私核验时，偏好把端侧推理、普通联网请求和媒体上传分开报告；没有授权后的 runtime 抓包时，不把静态代码审计表述成“绝不上传摄像头画面”。

## 三、Codex 可复用规则清单

1. 每个 workspace 先读 `AGENTS.md` 和它要求的规则文件，再执行任务。
2. 找文件先看目录路由，再用 `rg`；不要上来全盘搜索。
3. 遇到“怎么做 X”先查 `rules/skills/INDEX.md`，再查系统工具。
