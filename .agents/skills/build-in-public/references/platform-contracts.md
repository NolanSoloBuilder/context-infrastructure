## Progress Packet

用户可以直接按下面的最小模板提供材料。缺项不阻塞写作，但不得自行补造。

```markdown
项目：
时间范围：
这次做了什么：
为什么做：
最难或最意外的地方：
做了什么选择：
结果或证据：
我现在的想法：
下一步：
不能公开的信息：
希望吸引的人：
```

如果材料来自仓库，优先提取同样的字段。commit message 只能作为线索，最终描述还要结合 diff、测试或用户说明。

## 内容选择

多个进展按以下顺序评分：

1. 对读者判断的改变程度
2. 证据具体程度
3. 与目标受众的相关度
4. 当前公开时机

常用内容类型：

- Shipping：交付了什么，真实状态是什么
- Decision：为什么选择 A，放弃 B
- Failure：哪里失败，如何确认原因
- Learning：开发之后改变了什么认识
- Behind the scenes：一个通常看不到的实现约束
- Ask：展示明确上下文后，向同行征求具体反馈

纯粹的“今天写了几个页面、修了几个 bug”需要继续追问其影响。没有影响或认识时，更适合留在开发日志里。

## 小红书合同

### 标题

- 默认提供 3 个候选并推荐 1 个。
- 控制在 20 个汉字以内，标点也计入。
- 优先写具体对象、变化或真实矛盾。
- 避免“所有人都不知道”“必看”“轻松月入”等未经证实的承诺。

### 正文

推荐顺序：

1. 用 1 至 3 行交代具体变化或意外发现。
2. 补充目标与约束，让非项目成员也能理解。
3. 写关键选择、失败或实现过程。
4. 给出可核验结果。
5. 写改变后的判断与下一步。
6. 用一个具体问题邀请交流。

正文允许有个人语气，但不添加用户没有表达过的兴奋、焦虑、后悔或成就感。

### 标签与封面

- 默认使用 3 至 6 个直接相关标签。
- 产品名、技术方向、独立开发和具体问题优先于泛流量标签。
- 封面短句只概括主题，不重复堆叠标题，也不承诺正文没有的结果。

## X 合同

### 单帖

默认结构：

1. Observation：先写改变判断的观察、结果或选择。
2. Evidence：给一个具体事实。
3. Takeaway：给出当前认识或下一步。

一条帖子只承载一个主判断。默认不堆叠 hashtag；需要链接时只保留一个主要链接。

### Thread

只有以下情况使用 thread：

- 结论依赖连续的因果链
- 有 2 项以上必须分别解释的关键证据
- 用户明确要求过程复盘或教程

推荐顺序：

1. 主判断与为什么值得读
2. 原始目标和约束
3. 做过的选择或失败
4. 结果证据
5. 得到的认识与下一步

每条都应独立推进叙事。不要把一段长文按字符数机械截开。生成后如需发布，使用 Typefully 的 weighted count 校验每一条。

## 隐私与真实性门禁

写作前移除或泛化：

- 密钥、token、cookie、账号标识和未公开链接
- 内部域名、环境地址、客户数据和私有仓库细节
- 未经同意的姓名、头像、聊天截图和原话
- 可被组合识别的收入、交易或精确业务数据
- 尚未公开的发布日期、合作方和商业计划

无法判断能否公开时，将信息放入“待确认”，不写入帖子。用户可以主动确认后再补回。
